# 면접 답변 평가 기준 — Worker PRD

> 리포트 생성 파이프라인이 면접 답변을 평가할 때 따르는 기준. 이 문서는 **자기완결**이다 —
> 평가 프롬프트·검증 코드는 이 문서의 기준을 그대로 이행해야 하며, 기준 변경은 이 문서를 먼저 고친다.
>
> **분담**: 점수 집계 산식(영역 점수 = 답변별 평균, overall = 평가된 축 평균)과 jsonb 스키마의
> 정의 원천은 백엔드(`Kkori-Backend` `docs/requirements/report/report.md` §1)다. 반대로
> **답변별 점수를 어떻게 매기는지(루브릭)와 약점 태그 어휘집의 정의 원천은 이 문서**다 —
> 백엔드는 태그를 불투명 문자열로 취급한다.

## Overview

Worker는 면접 세션의 대본(질문-답변)과 면접에 사용된 이력서 데이터를 입력으로, 답변마다
텍스트 3축 점수·피드백·약점 태그·개선 과제를 산정하고 세션 총평을 생성한다.

- 평가 단위: **질문-답변 쌍 1개** (대본의 questionNumber 기준, 꼬리 질문도 독립된 1개)
- 평가 입력: 해당 답변 + 그 질문의 주제 맥락(같은 parentQuestionNumber의 선행 문답) + 이력서 근거
- 산출: 답변별 `{텍스트 3축 점수, feedback, weaknessTags, improvementTasks, resumeContext}` + 세션 `{총평, 영역 점수, 태그 요약}`
- 원칙: **LLM의 재량은 답변별 판정까지다.** 집계(평균·요약)는 전부 결정적 코드가 수행한다.

## 1. 점수 산정 — 루브릭 앵커 방식

LLM에게 0~100 숫자를 자유 산정시키면 실행마다 분산이 크다. 대신 축마다 **5단계 기준문(앵커)**을
주고, ① 답변이 가장 가까운 앵커를 고른 뒤 ② 그 앵커 값에서 ±10 이내로 조정한 **정수**를 내게 한다.
출력은 tool-use(스키마 강제)로 받아 0~100 범위를 검증한다.

### 1.1 논리성 (logicScore) — 주장과 근거의 구조

| 앵커 | 기준 |
|---|---|
| 100 | 결론을 먼저 말하고, 근거가 결론을 직접 뒷받침하며, 흐름에 비약이 없다 |
| 80 | 구조(주장-근거)는 갖췄으나 일부 연결이 느슨하거나 결론이 뒤에 온다 |
| 60 | 주장과 근거가 있지만 순서가 뒤섞여 흐름을 따라가기 어렵다 |
| 40 | 사실 나열 위주로, 무엇을 주장하는지 흐릿하다 |
| 20 | 앞뒤가 모순되거나 질문과 무관한 방향으로 전개된다 |

### 1.2 구체성 (specificityScore) — 실제 경험·세부의 밀도

| 앵커 | 기준 |
|---|---|
| 100 | 수치·구체적 기술명·상황이 담긴 실제 경험으로 답한다 |
| 80 | 사례는 있으나 세부(수치·본인 역할·결과)가 부족하다 |
| 60 | 일반론이 중심이고 사례는 짧게 스치듯 언급된다 |
| 40 | 추상적 서술 위주로, 답변자가 겪은 일인지 판별이 어렵다 |
| 20 | 원론·교과서 문장뿐, 경험이 없다 |

### 1.3 기술 정확성 (technicalAccuracyScore) — 개념의 옳음과 깊이

| 앵커 | 기준 |
|---|---|
| 100 | 개념이 정확하고, 전제·한계·트레이드오프까지 언급한다 |
| 80 | 대체로 정확하나 사소한 부정확이나 과한 단순화가 있다 |
| 60 | 핵심은 맞지만 중요한 부분을 얼버무리거나 깊이가 없다 |
| 40 | 개념 혼동이 뚜렷하다 (용어와 실체가 어긋남) |
| 20 | 설명이 틀렸다 |

- 기술 정확성 판정 시 **이력서 근거를 함께 제시**한다 — 답변이 이력서의 기술 경험과 상충하면
  (예: 이력서에 깊이 있게 쓴 기술을 전혀 설명 못함) 감점 근거로 쓰고 resumeContext에 남긴다.
  **(보류 — §6 참고: 이력서 연동 도입 전까지 미구현)**

### 1.4 모르는 질문에 대한 답변 — 정직이 손해 보지 않는 서열

"모른다"고 인정하는 것과 아는 척 틀리게 설명하는 것을 구분한다. 실전 면접의 인센티브와
일치시키는 것이 목적이다 — **아는 척하다 틀리는 것이 최악이고, 정직한 인정은 그보다 위다.**

| 답변 유형 | 산정 |
|---|---|
| 모름 인정 + 아는 범위에서 접근 시도 ("정확히는 모르지만 ~와 비슷하다면…") | 시도 내용을 정상 루브릭으로 평가 (60대까지 가능) |
| 순수한 모름 인정 ("모르겠습니다"만) | 세 축 모두 30~40 |
| 아는 척 틀린 설명 | 기술 정확성 20 (최하) |
| 무응답·중도 포기 | 세 축 모두 20 이하 |

- 순수한 모름 인정에는 "기술 개념 오류" 태그를 달지 않는다(오류가 아니라 공백) — "깊이 부족"이 맞다.
- 이 경우 피드백은 인정 자체를 긍정하고, 아는 개념과 연결해 접근하는 시도를 권하는 내용으로 쓴다
  (예: "모르는 것을 인정한 건 좋은 선택이에요. 아는 개념과 연결해 추측을 시도해보면 더 좋아요").

## 2. 약점 태그 어휘집 (정의 원천: 이 문서)

태그는 **아래 목록에서만** 선택한다(자유 생성 금지 — 집계·후속 면접 질문 반영을 위해).
답변당 0~3개. 태그 문자열(한글 라벨)이 곧 코드다 — 백엔드·프론트는 그대로 저장·표시한다.

### 2.1 텍스트 기반 (MVP 활성 — 12개)

| 태그 | 판정 기준 |
|---|---|
| 두괄식 부족 | 결론·핵심이 답변 끝에 나오거나 나오지 않음 |
| 근거 부족 | 주장은 있으나 수치·사례 등 뒷받침이 없음 |
| 구체성 부족 | 서술이 추상적이고 실제 경험의 세부가 없음 |
| 장황함 | 핵심 대비 분량이 과함, 같은 말 반복 |
| 질문 이탈 | 질문의 요지와 다른 내용으로 답함 |
| 기술 개념 오류 | 기술 설명이 부정확하거나 틀림 |
| 깊이 부족 | 표면적 이해에 머무름 (왜/어떻게 설명 불가) |
| 용어 남용 | 전문 용어를 설명 없이 나열 |
| 경험 연결 부족 | 이력서의 관련 경험이 있는데 활용하지 못함 |
| 답변 미완성 | 말을 끝맺지 못하거나 중간에 포기 |
| 앞뒤 불일치 | 같은 세션 내 다른 답변과 모순 |
| 대안 검토 부족 | 선택·결정을 말하며 대안이나 트레이드오프를 언급하지 않음 |

### 2.2 음성 기반 (2단계 음성 분석 — 4개, 판정 규칙은 `delivery-score.md` §5)

음성 태그는 LLM이 아니라 **오디오 분석이 결정적 규칙으로 판정**한다. 세션 단위로 판정하며
`weakness_tag_summary` 에 텍스트 상위 3개 뒤에 덧붙인다(답변별 `weakness_tags` 에는 들어가지 않는다).

| 태그 | 풀이 | 상태 |
|---|---|---|
| 말 속도 빠름 | 적정 범위보다 빠르게 말함 | 활성 |
| 말 속도 느림 | 적정 범위보다 느리게 말함 | 활성 |
| 잦은 침묵 | 답변 중 긴 침묵이 자주 발생 | 활성 |
| 군말 잦음 | "음…", "어…", "그…"처럼 뜻 없이 채우는 말이 자주 나옴 | **미판정** — STT 대본이 군말을 걷어내고, 오디오만으로 가려낼 결정적 규칙이 없다 |

### 2.3 어휘집 변경 규칙

- 태그 추가·삭제·개명은 이 문서를 먼저 고치고, 프롬프트의 태그 목록과 함께 한 커밋으로 변경한다.
- 개명은 기존 저장 데이터와의 단절을 만들므로(집계가 다른 태그로 취급) 원칙적으로 피하고,
  불가피하면 백엔드와 마이그레이션을 합의한다.

## 3. 답변별 피드백 (feedback)

- 1~2문장. **행동 가능한 지적 1개**에 집중한다 — 여러 문제가 보여도 가장 점수를 깎은 것 하나.
- 문체는 존댓말 제안형("~하면 더 좋아요"), 비난·단정 금지.
- 잘한 답변(세 축 모두 80 이상)이면 강점을 짚는 칭찬 1문장으로 갈음한다.

## 4. 개선 과제 (improvementTasks)

- 답변당 **0~2개**. 약점 태그와 연결된 것만 만든다 (태그 없는 답변엔 과제도 없음).
- 형식: `{title, description}` — title은 행동 지시형 짧은 제목(25자 이내 권고),
  description은 구체적 실행 방법 1문장.
- 예: `{"title": "결론부터 말하기 (PREP)", "description": "답변 첫 문장에 핵심 결론 배치"}`
- **title 길이의 강제 방식**: 25자는 프롬프트로 지시하는 권고다 — 결정적 상한으로
  강제하면 잘라낸 제목이 문장을 훼손하거나, 재호출 비용이 부가 정보 대비 과하다.
  구현(후처리)은 화면 표시를 깨는 극단값만 거른다: **50자를 넘는 제목의 과제는
  절단하지 않고 통째로 제외**한다.

## 5. 세션 총평 (summary)

3~5문장, 이 순서로 구성한다:

1. **강점 1개** — 세션 전체에서 가장 잘한 지점 (없으면 시도 자체의 인정)
2. **약점 패턴** — 반복 등장한 약점 태그 기준 (단발성 실수는 언급하지 않음)
3. **다음 면접을 위한 조언** — 약점 패턴을 고치는 우선순위 1개

## 6. 이력서 근거 (resumeContext)

> **보류 (2026-08-03)**: 이력서 발췌 주입과 resumeContext 산출은 아직 구현되지 않았다 —
> 현재 평가 입력은 대본뿐이고 resume_context 컬럼은 항상 비워 저장한다.
> 이력서 연동(평가 품질 스토리)에서 도입 예정.

- 평가에 실제로 인용한 이력서 내용의 발췌를 답변별로 저장한다 — 이력서가 이후 수정·삭제되어도
  리포트가 자기완결로 성립하는 근거(백엔드 PRD의 스냅샷 원칙).
- 인용이 없으면 비워 둔다. 구조는 Worker 자유(백엔드는 불투명 취급).

## 7. 집계 (결정적 코드 — LLM 아님)

백엔드 PRD §1 점수 체계의 이행 확인용 요약 (정의 원천은 백엔드):

- 영역 점수(REPORT_SCORES의 3축) = 답변별 해당 축 점수의 **평균(반올림)**
- `overall_score` = 평가된 축 점수의 평균(반올림) — 전달력 미평가면 텍스트 3축 평균
- `weakness_tag_summary` = 전체 답변의 태그 빈도 **상위 3개** `[{tag, count}]` + 음성 태그(뒤에 덧붙임, `delivery-score.md` §5)
- `delivery_score` = 세션 녹음에서 결정적 산식으로 산출 — `delivery-score.md` §4
