## 1. 워커는 별도 레포 — 백엔드 안에 두지 않는다

**결정**: 워커는 `Kkori-Worker`(독립 git repo). 백엔드 `Kkori-Backend` 안의 서브디렉터리가 아니다.

**왜**: 언어·런타임·배포 주기·의존성이 완전히 다르다(Python/uv/FastStream vs Java/Gradle/Spring). 한 레포에
섞으면 CI·의존성 그래프·리뷰 도구가 두 세계를 억지로 공유한다. "백엔드와 연동이 쉬울 것"이라는 이유로
같이 두려 했지만, 연동의 실체는 **코드 공유가 아니라 계약 공유**(Redis 스트림 필드·상태 enum)라 레포가
같을 필요가 없다. 계약은 문자열 메시지로 언어 경계를 넘는다.

**대가**: 계약이 두 레포에 물리적으로 나뉘어 산다 → §4(자기완결 사본)로 관리.

💬 **면접 포인트**: "폴리글랏 서비스를 모노레포 vs 멀티레포 어디에?" — 결합의 축이 코드인지 계약인지로 판단.
언어 경계를 넘는 결합은 메시지 계약이라 레포 분리가 자연스럽다.

## 2. 메시지 처리 프레임워크: FastStream (vs Celery)

**결정**: FastStream 0.7.1 (Redis 브로커). Celery 아님.

**왜**:

| 축 | FastStream | Celery |
|---|---|---|
| 모델 | **브로커 네이티브**(스트림 구독/발행이 1급) | 태스크 큐(작업 디스패치 중심) |
| async | **native async/await** (AI·S3 I/O 대기에 적합) | 주로 동기 워커(prefork), async는 곁다리 |
| Redis Streams | 소비자 그룹·ACK를 그대로 노출 | Streams를 1급으로 다루지 않음 |
| 계약 | pydantic 모델로 메시지 스키마 = 코드 | 태스크 시그니처(인자)가 계약 |
| 무게 | 얇음, 브로커 스위칭 용이 | 무겁고 기능 많음(스케줄러 등) |

우리 워크로드는 "이력서 1건 = 여러 외부 I/O(S3 다운로드·Bedrock 2종 호출·DB)를 대기하는 async 파이프라인"이라
native async + Redis Streams 소비자 그룹을 1급으로 다루는 FastStream이 결이 맞는다. Celery의 강점(주기 태스크
스케줄링, 방대한 생태계)은 지금 필요 없다.

**대가**: Celery보다 생태계·레퍼런스가 적다(신생). 운영 노하우가 덜 쌓임.

💬 **면접 포인트**: "Celery 안 쓴 이유" — 태스크 큐 vs 브로커 네이티브. I/O 바운드 async 파이프라인 + Streams
소비자 그룹이 필요하면 후자. 프레임워크는 워크로드 모양으로 고른다.

## 3. Redis Streams (vs Pub/Sub / List)

**결정**: 요청 채널은 **Redis Streams + Consumer Group + XACK**. (백엔드가 이미 Stream으로 발행.)

**왜 — 전달 보장이 채널마다 다르다**:

| 방식 | 보존 | 재소비 | 우리 용도 적합성 |
|---|---|---|---|
| Pub/Sub | 없음(구독자 없으면 소실) | 불가 | ✗ 워커 다운 중 요청 증발 |
| List(BLPOP) | 있음(FIFO) | 소비 시 제거 → PEL 없음 | △ ACK·재처리 없음 |
| **Streams+Group** | 있음(로그) | **PEL·XACK·XAUTOCLAIM** | ◎ at-least-once 재처리 |

이력서 분석은 **유실되면 안 되는 작업**이다. 워커가 처리 중 죽으면 메시지가 PEL(Pending)에 남아
XAUTOCLAIM으로 회수·재개할 수 있어야 한다. 이건 Streams 소비자 그룹만 제공.

- 반대로 **상태 채널(status.changed)은 유실 허용** → 백엔드는 SSE 중계에 auto-ack(부기 없음)로 소비.
  "같은 Redis, 다른 채널, 다른 보장" — 전달 보장 요구가 기술 선택을 가른다.

**딸린 결과**: at-least-once → **멱등성 필수**(§5), 중복·회수 경합 방어(원자적 상태 CAS) 필요.

💬 **면접 포인트**: "Pub/Sub vs Stream", "at-least-once와 멱등성", "PEL/XACK/XAUTOCLAIM로 크래시 복구",
"한 시스템 안에서 채널마다 보장을 다르게 두는 이유".

## 4. 계약은 워커 레포에 자기완결 사본으로 둔다 (변경 권한은 백엔드)

**결정**: 워커 PRD가 계약(스트림 필드·상태 8종·StructuredData)의 **전체 사본**을 담는다. 단, **바꿀 권한은
백엔드**에 있고 워커는 소비자로서 따른다.

**왜 사본인가**: 크로스 레포라 **워커의 CodeRabbit·CI는 백엔드 레포를 볼 수 없다.** "백엔드 문서를 참조"는
워커 리뷰 시점에 물리적으로 열리지 않으므로 무의미 → 계약을 워커 안에 물리적으로 복제해야 리뷰·개발이 성립.

**왜 권한은 백엔드인가**: 계약의 실제 소유자는 **발행자이자 상태 엔티티의 주인**인 백엔드다. 사본을 가졌다고
워커가 계약을 바꿀 수 있는 건 아니다 — "물리적 위치(사본)"와 "변경 권한(백엔드)"을 분리.

**계약 불일치 방어 — 계약 예시 대조 테스트**: 사본은 알아채지 못한 채 어긋날 수 있다. 실제 스트림 필드맵 예시(JSON)를 워커에
계약 예시 파일로 커밋하고, **요청 decode(문자열맵→pydantic) + 상태 encode(모델→문자열맵) 양방향**을 그 예시와
대조하는 테스트를 둔다. 계약이 바뀌면 예시 파일도 바뀌고 그 변경이 PR diff에 **그대로 드러난다**. (백엔드의 "계약 record의
`toMap()`을 테스트가 그대로 쓴다"와 같은 방식 — 계약을 컴파일/테스트가 붙잡게 한다.)

**대가**: 두 곳을 수동 동기화. 백엔드 record 변경 시 워커 계약 예시·모델을 손으로 맞춰야 함(자동 전파 없음).

💬 **면접 포인트**: "언어·레포 경계를 넘는 계약을 어떻게 관리하나" — SSOT의 두 얼굴(변경 권한 vs 물리 사본)을
분리, 크로스 레포 리뷰 도구의 가시성 한계, 계약 예시 대조로 불일치를 테스트로 막기.

## 5. 멱등성 & 크래시 복구 = DB 상태 기준 체크포인트

**결정**: 진입 지점은 **DB 상태가 결정**(mode는 cross-check). 각 단계 진입을 **원자적 상태 CAS**로,
산출물 저장과 상태 전이를 **한 트랜잭션**으로.

**왜**: at-least-once(§3) + XAUTOCLAIM 회수는 "안 죽은 원본 + 회수본"이 경합할 수 있다. "resumeId 멱등"만으론
이중 처리를 못 막는다. `UPDATE ... SET status='PARSING' WHERE status='UPLOADED'`처럼 CAS로 전이하고 **영향
행이 0이면 조용히 양보** → 앞서간 처리자가 이미 있다는 뜻.

**두 재개 불변식**(둘 다 "상태가 진실")：
1. **산출물 커밋 후 상태 갱신** — data 저장 뒤에 PARSED. 반대면 "PARSED인데 data 없음"으로 재개가 깨짐.
2. **재개 분기는 상태 컬럼만 본다, 산출물 존재로 판단 금지** — FULL 재분석은 상태를 UPLOADED로 리셋하지만
   이전 런의 `structured_data`는 **DB에 남아 있다**. 산출물 보고 "임베딩부터" 판단하면 **낡은 데이터로 색인**.

**임베딩 진입 시 항상 기존 청크 선삭제** 후 재생성(EMBEDDING 재개·REINDEX·부분 실패 공통) → 중복/유령 청크 방지.

💬 **면접 포인트**: "at-least-once에서 정확히 한 번 효과내기"(멱등·CAS), "체크포인트를 산출물이 아니라 상태로
잡는 이유", "동시 처리 경합을 락 없이 막기"(조건부 UPDATE의 영향 행 수).

## 6. 포기 규칙 & DLQ 미도입 & retry_count 소유권

**결정**:
- **포기**: 수신·회수 직후 처리 전에 delivery count 확인, 임계(3) 이상이면 재처리 없이 **① `FAILED` 기록 →
  ② XACK** (이 순서 고정, ①은 멱등).
- **DLQ 스트림 안 만든다**: 메시지의 모든 필드가 **DB에서 재유도 가능한 포인터**라 격리 보존할 고유 정보가 없다.
  재처리는 스트림 재주입이 아니라 **재분석 API가 DB에서 새 메시지를 생성**. 격리 건은 `FAILED` 레코드가 겸함.
- **`retry_count`는 Worker 소유**(서버 read-only). **delivery count(Redis PEL)와 다른 카운터** — 전자는
  "런 내부 재시도"(Worker DB 기록), 후자는 "메시지 전달 횟수"(Redis 관리). 서로 파생 안 됨.

**왜 순서가 FAILED→XACK인가**: 중간에 죽어도 재전달본이 같은 경로를 다시 타 수렴(①이 멱등이라 이미 FAILED면
그대로). 반대로 XACK 먼저면 FAILED 기록 전에 죽을 때 "종결도 실패도 아닌" 미아가 생김.

**왜 DLQ가 과한가**: DLQ의 가치는 "재처리에 필요한데 원본에만 있는 정보를 격리 보존"인데, 여기 메시지는
포인터(resumeId 등)뿐이라 보존할 게 없다. `FAILED`가 같은 일을 더 단순하게 한다(같은 테이블에서 조회·구분).

💬 **면접 포인트**: "실패 메시지 어디로 보내나" — DLQ가 항상 답은 아니다, 메시지가 포인터면 상태 레코드가 대체.
"쓰기 두 개의 순서"(FAILED→ACK)로 크래시 창을 닫기, "두 재시도 카운터의 구분".

## 7. AI 스택: Claude Haiku 4.5 (구조화) + Cohere Embed Multilingual v3 (임베딩)

**결정**: 구조화 LLM = **Claude Haiku 4.5(Bedrock)**, 임베딩 = **Cohere Embed Multilingual v3, `vector(1024)`**.

**구조화 LLM — 왜 Haiku**:
- 작업이 "PDF 텍스트 → 고정 스키마(§StructuredData) JSON"이라 **추론 난도보다 스키마 준수**가 핵심 →
  tool-use/JSON 스키마 강제가 되는 모델이면 충분. Haiku가 그걸 저렴하게(Sonnet 대비 **정확히 1/3**: $1/$5 vs
  $3/$15 per 1M in/out) 한다.
- **승급 경로가 무리스크**: 한국어 파싱 품질이 부족하면 Sonnet 4.6으로 교체 — 스키마·DB 영향 0(출력 형태 동일).
  그래서 싼 쪽에서 시작해도 손해가 없다.
- 비-Claude 대안(Nova 등)도 있으나 tool-use JSON 신뢰도·품질 마진에서 Claude 우선.

**임베딩 — 왜 Cohere v3 (vs Titan V2)**:

| | Cohere Embed ML v3 | Titan Embed V2 |
|---|---|---|
| 차원 | 1024 | 1024 |
| 한국어/다국어 | **강함** | 약함 |
| 단가 | 비쌈(~5배) | 쌈 |
| 비대칭 임베딩 | `search_document`/`search_query` | 없음 |

이력서 RAG의 본질은 **한국어 검색 품질**이라 다국어 약한 Titan은 탈락. 비용차(~5배)는 이력서 볼륨에선 무시
가능(1만 건 ≈ $3). 색인은 `input_type=search_document`, 질의는 `search_query`로 **비대칭 임베딩** — 문서/질의를
다른 공간 취급해 검색 정확도를 올린다.

**스키마 소유권**: `resume_chunks`(content, metadata, `embedding vector(1024)`) + `CREATE EXTENSION vector`는
**Worker 소유**(유일 writer이자 임베딩 차원의 주인). 차원 1024는 **Cohere v3에 종속** — 모델 교체 시 여기만 조정.
백엔드는 `resumes`/`structured_data` 소유.

**운영 주의**: Bedrock은 **로컬 에뮬레이터가 없다**(MinIO=S3와 다름). 로컬 워커도 실제 Bedrock 호출 → AWS 자격·
리전 필요, 로컬에서도 과금. 서울 리전 모델 가용성 제한 가능 → **us-east-1 폴백**을 config에.

💬 **면접 포인트**: "LLM/임베딩 모델 선택 기준" — 작업이 추론이냐 형식준수냐(→ 싼 모델+스키마 강제), 검색은
도메인 언어 품질 우선(비용은 볼륨으로 환산). "비대칭 임베딩", "임베딩 차원이 스키마를 잠근다(교체 비용)".

## 8. REINDEX 진입 상태: Spring이 발행과 같은 트랜잭션에서 세팅

**결정**: 런의 초기 상태를 **Spring이 발행과 같은 트랜잭션에서** 세팅한다 — FULL→`UPLOADED`,
REINDEX→`EMBEDDING`(백엔드 `restartFor()`).

**왜 — 설계 모순을 없앤다**: 원래 "Spring은 UPLOADED만 기록 + 워커는 순수 상태 기준"이었는데, REINDEX는
구조화를 건너뛰고 임베딩부터여야 한다. 만약 REINDEX도 UPLOADED로 진입하면 워커의 상태 기준 재개가 처음부터
돌려 **LLM이 사용자 수정본을 덮어쓴다**. Spring이 진입 상태를 EMBEDDING으로 세팅하면 워커는 상태 기준만 유지해도
자연히 임베딩부터 탄다. 부수 효과로 **REINDEX 중복 전달도 멱등**(완료 시 EMBEDDED→이후 스킵).

- 원칙 정리: "Spring은 UPLOADED만" → "Spring은 **런의 초기 상태**를 기록". 이후 파이프라인 전이는 여전히 전부 워커.
- **cross-check로 시끄럽게**: mode와 상태가 규약과 어긋나면(REINDEX인데 UPLOADED 등) 경고 후 진행이 아니라
  **`FAILED`로 종결** — 조용한 오염보다 시끄러운 실패.

💬 **면접 포인트**: "재색인/재처리에서 어디서부터 다시 하나" — 진입 상태를 발행자가 트랜잭션으로 세팅해 소비자를
단순 상태 기계로 유지. "계약 위반을 조용히 넘기지 않기(loud failure)".

## 9. 청킹: 엔티티 기반 + 오버플로 분할 (C)

**결정**: `structured_data`의 **엔티티 경계를 청크 경계로** — 프로젝트/경력/스킬 카테고리당 1청크, 초장문
엔티티만 문장 경계로 분할. (PRD §2.5)

**왜 — 입력이 이미 구조화돼 있다**: 청킹 입력은 raw text가 **아니라** profile/skills/projects/experiences로
구조화된 JSON(원문 미저장). 고정 길이 슬라이딩 윈도우는 raw text에서 구조를 **찾으려는** 기법인데, 우리는 구조를
**이미 갖고 있다** → 그걸 버리고 잘라 섞을 이유가 없다.

**대안 비교**:

| 전략 | 검색 정확도 | 자기완결성 | 문제 | 판정 |
|---|---|---|---|---|
| A. 고정 길이 슬라이딩 | △ 경계서 잘림·혼합 | △ | 있는 구조를 버림 | ✗ |
| **C. 엔티티 기반 + 오버플로 분할** | ◎ 의미경계=검색단위 | ◎ | 초장문만 분할 필요 | **채택** |
| D. 전체 1청크 | ✗ 어느 프로젝트인지 못 집음 | ○ | 세밀검색 불가 | ✗ |
| E. 필드 초세분화 | △ 과분할 | ✗ "Java"만 든 청크 무의미 | 문맥 파편화·청크 폭증 | ✗ |
| F. 계층형 parent-child | ◎ | ◎ | 부모-자식 저장 복잡 | △ 미래 |

**핵심 규칙**: profile은 임베딩 제외(질문 소스 아님), 자기완결 라벨 prepend(`[프로젝트] {name} · 역할 {role}...`),
초장문만 문장 분할+헤더 반복+소량 오버랩, 빈 것은 청크 0개(→ 0청크 EMBEDDED 종결).

**왜 지금 확정해도 안전한가 — 되돌릴 수 있다**: 청킹은 순수 워커 내부 로직이라 **계약·임베딩 차원 불변**.
바꾸면 코드 수정 + **REINDEX 한 바퀴로 백필**(DDL 마이그레이션 없음). 임베딩 모델 교체(차원 바뀌면 스키마까지)
보다 싸다. 백필 대상 식별용으로 `metadata.chunk_version`을 심어둔다. → 첫 버전을 과튜닝하지 않고, 검색 품질을
실측하며 파라미터나 F(계층형)로 승급.

💬 **면접 포인트**: "청킹 전략을 무엇으로 정하나" — **입력이 raw text냐 구조화 데이터냐**가 가른다. 구조가 있으면
그 경계가 곧 검색 단위. "청킹은 되돌릴 수 있는 결정"(REINDEX 백필, 차원 불변)이라 초기에 과설계 불필요.
