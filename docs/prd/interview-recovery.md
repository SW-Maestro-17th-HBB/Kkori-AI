# 면접 재연결·복원

> **User Story**: HBB1-308 — 나는 사용자로서 연결이 끊겨도 면접을 이어갈 수 있다.
>
> **하위 이슈**: HBB1-309 [개발] 재연결 대기 처리 개발 · [개발] 면접 상태 복원 개발(이슈 생성 예정)

## Overview

진행 중인 면접이 연결 문제로 끊겼을 때 면접을 이어가는 기능 영역이다. `agent/`(kkori-agent)의 LiveKit 음성 에이전트 프로세스에서 실행되며, 두 층위를 다룬다 —

1. **재연결 대기 처리**: agent 프로세스가 살아있는 동안 candidate가 이탈하면, 세션을 즉시 종료하지 않고(현행 기본값 변경 — `close_on_disconnect=False`) 재연결 창 동안 유지한다. 창 내 재입장 시 면접을 재개하고, 창 소진 시 종료로 수렴한다.
2. **면접 상태 복원**: agent 프로세스 자체가 소실된 뒤 Spring이 재디스패치한 새 잡이, agent 소유 Redis 상태(세션 메타·대화 사본)를 읽어 경과 시간·대화 맥락·종료 국면을 복원하고 면접을 재개한다. 지금까지 쓰기만 하던 Redis write-through 사본(`docs/prd/interview-end.md` §4 — "Redis의 역할은 Agent 복원뿐")을 처음으로 읽는 스토리다.

핵심 데이터 흐름: candidate 이탈 관측 → 재연결 deadline 내구 기록 + 창 타이머(시계는 계속 흐른다) → 재입장 시 재개 안내·앵커 발화 / 창 소진 시 종료 수렴(시간 기준 이원화 — 아래) ‖ agent 소실 → Spring 판별 ③(행·표식 둘 다 없음) → `AGENT_LOST` 유예 내 재디스패치 → Redis 상태 복원(잔여 창·경과 시간·대화·종료 국면) → 재개.

**종료 의미론(시간 기준 이원화 — 확정)**: 끊김 관련 종료 수렴은 시간 기준으로 나뉜다 —

| 상황 | 수렴 | 근거 |
| --- | --- | --- |
| 시간이 남았는데 재연결 창 소진 | flush 생략 → 룸 삭제 → `room_finished` + 행 없음 → Spring `ABORTED` | 면접은 완주되지 않았다 — "행 = 정상 종료의 증거" 불변식 유지 |
| 창·복원 도중 hard 시한 선(先)소진 | 정상 종료 시퀀스(flush → 행 기록) → `ENDED` | 면접은 사실상 완주됐다 — 수십 분의 대화를 버리지 않고 리포트를 제공한다 |

**크로스 레포 계약 변경(명시)**: 이 스토리는 Spring 상태 머신(HBB1-294)의 전제를 바꾼다. 현행 매핑에서 candidate 이탈이 no-op인 것은 "에이전트도 즉시 종료하므로 에이전트 이탈 경로가 이어서 처리한다"는 전제였다. 에이전트가 재연결 창 동안 세션을 유지하면 에이전트 이탈 이벤트가 오지 않으므로, Spring의 상태 전이가 새로 필요하다. **다음을 백엔드 스토리의 완료 조건으로 이관한다** —

1. candidate 이탈 → `INTERRUPTED` 전이(신설).
2. **candidate 재입장 → `INTERRUPTED` → `ACTIVE` 복귀 전이**(신설 — 재입장 webhook 기준. 없으면 agent가 면접을 재개해도 Spring 상태가 `INTERRUPTED`로 남는다).
3. 재디스패치 성공 시의 기대 전이(확정 — 구현은 백엔드 소유, 출발·도착 상태는 이 계약을 따른다): agent 입장 관측 시 `AGENT_LOST` → candidate 재실이면 `ACTIVE`, 부재면 `INTERRUPTED`(이후 재입장·창 소진 규칙은 동일 적용). 재연결 창·유예 타임아웃 시 `ABORTED` 수렴.
4. 재입장 토큰: **최초 입장과 동일 identity 보장**(agent의 candidate 식별 전제 — §1), 만료는 agent와 같은 재연결 deadline 기준(§1 — 관측 시각 수 초 편차 감수).
5. **활성 dispatch 단일성 보장**: 같은 세션에 두 agent 잡이 동시에 살아있지 않도록, 재디스패치는 상태 CAS로 정확히 1회 실행하고 기존 dispatch의 종료를 확인(또는 삭제) 후 생성한다. **이것이 동시 잡에 대한 유일한 안전 보장이다** — agent 측 `owner` 검사(§2)는 원자성이 없는 관측·완화 계층이다.

**범위**: `interviewType=THIRTY_MIN`만 다룬다. 다음은 범위 외 — Spring 측 전이·재디스패치·재입장 토큰(백엔드 스토리 병행 — 위 완료 조건 목록만 계약으로 정의), 프론트 재연결 UX, 5분 CS 유형, 탈퇴 연계, 종료 시퀀스 자체(`docs/prd/interview-end.md` — 이 문서는 그 위의 진입 경로만 추가한다), 재연결 창 동안 시계를 멈추는 방식(기각 확정 — §1).

### 기능 요구사항

| No. | Function | Description |
| --- | --- | --- |
| 1 | 재연결 대기 처리 | candidate 이탈 시 세션을 재연결 창 동안 유지하고, 창 내 재입장 시 면접 재개, 창 소진 시 시간 기준 이원화로 종료 수렴 |

## 1. 재연결 대기 처리

### 설명

candidate 이탈이 면접의 끝이 아니게 한다 — agent 프로세스가 살아있는 한, 이탈은 "재연결 창의 시작"이다.

- **세션 유지(`close_on_disconnect=False`)**: 참가자 퇴장 시 세션 즉시 종료(현행 기본값)를 끄고, agent가 이탈·재입장을 직접 관장한다. livekit-agents `RoomInputOptions.close_on_disconnect=False` 사용(1.6.6 지원 확인).
- **candidate 식별 = 최초 identity 고정(확정)**: 최초 입장 관측 시 candidate의 participant identity를 세션 메타(§2)에 기록하고, 이후 **재입장 판정은 identity 일치로만** 한다. "첫 번째 remote 참가자 복귀" 같은 위치 기반 판정은 하지 않는다 — 관전자·오입장·다른 identity를 candidate로 오인하는 경로를 차단한다. identity 불일치 참가자는 재개 판정에서 무시하고 로그만 남긴다(입장 자체의 거부·퇴출은 룸 권한 정책 — 범위 외). 전제: 재입장 토큰의 identity 동일 보장(Overview 계약 조건 4 — 백엔드가 보장 불가하면 계약 개정 필요).
- **재연결 창 = 3분(단일 계약값 — 확정)**: agent와 Spring이 같은 값을 각자 config 상수로 갖는 **단일 계약값**이다. 수렴 판정 주체는 agent다(룸에서 실제로 종료를 실행하는 쪽). 값은 config 상수 **[기본값 3분 — 실측 조정 여지]**. Spring의 `AGENT_LOST` 유예는 별개 값이다 — 그것은 "agent 소실 시 Spring의 판별 유예"이고, 재연결 창은 "candidate 부재를 agent가 버티는 시간"으로 역할이 다르다.
- **재연결 deadline의 내구 기록(확정 — 창은 절대 시각이다)**: 이탈 관측 시점에 `deadline = now + 창`을 **절대 UTC 시각으로 세션 메타(§2)에 기록**하고, 창 타이머·재입장 토큰 만료·복원 잡의 잔여 대기(§2)가 모두 이 deadline을 기준으로 한다. 창을 상대 시간으로만 관리하면 창 도중 agent가 소실됐다 재디스패치될 때 창이 3분씩 다시 부여된다(이탈 2:50 후 소실 → 총 5분 이상 대기) — deadline을 내구화해 **총 부재 허용 시간을 이탈 시점 기준으로 고정**한다. 재입장 시 deadline을 삭제하고, 다시 이탈하면 새 deadline을 기록한다(이탈마다 새 창 — 반복 끊김의 세션 수명은 시계가 계속 흐르므로 hard 시한이 상한이다). 기록 실패는 경고 후 창 타이머로 계속(내구화는 복원 층위의 재료다). Spring의 토큰 만료는 Spring 자신이 관측한 이탈 시각 기준으로 같은 창 값을 적용한다 — 양측 관측 시각의 수 초 편차는 감수한다(계약 조건 — Overview 4).
- **끊김 중에도 시계는 계속 흐른다(확정 계승 — interview-end.md §1)**: 재연결 창 동안 면접 시계를 멈추지 않는다. 창이 짧아 잠식이 제한적이고, 멈추면 반복 끊김으로 세션 수명이 비결정적이 되며, 연습 면접의 위험 성향(ADR-E3-10)과 일관된다. hard 안전망 타이머도 창 동안 계속 동작한다.
- **이탈 관측·입력 경계**: candidate의 `participant_disconnected` 관측 시점에 재연결 창을 시작하고, **진행 중이던 질문 생성·발화를 폐기**한다(청자 없음 — 기존 턴 무효화 메커니즘 재사용). STT의 부분 발화 finalize·큐에 남아 있던 turn 완료 콜백이 이탈 관측 **이후**(재입장 이후 포함)에 도착할 수 있으므로 — "창 동안 user turn은 없다"는 가정하지 않는다 — **이탈 전에 시작된 입력의 완료는 커밋하지 않고 폐기한다**: 부재 중 도착한 완료는 재실 검사로, 재입장 후 지연 도착한 완료는 **turn 완료 이벤트에 실린 발화 시작 시각과 직전 이탈 관측 시각의 대조**로 완료별 판정한다(끊김에 잘린 부분 답변은 신뢰할 수 없는 증거다. 시작 시각 미제공 시 재실 검사 폴백 — 미제공이 입력 전체를 막지 않는다). 재입장 후 재낭독 앵커(아래)가 해당 질문을 다시 묻는 것으로 수렴한다.
- **재입장 시 재개**: 창 내 candidate(identity 일치) 재입장 관측 시 deadline을 삭제하고 재개한다 —
  - **재개 안내 발화 = 검수 고정 문구**(코드 상수 — 초기 질문·클로징과 같은 원칙). 예: "연결이 복구되었습니다. 면접을 이어가겠습니다."
  - **재개 안내는 transcript에 커밋하지 않는다(확정)**: 면접 내용이 아닌 시스템 안내이고, 커밋하려면 소비자(리포트) 스키마 확장(`questionType` 추가)이 필요하다 — 발화 객체 스키마를 이 스토리에서 흔들지 않는다. "실제 들은 발화" 원칙의 명시적 예외로 기록한다.
  - **앵커(재개 안내 직후의 다음 행동 — 확정)**: 대화 로그의 마지막 발화가 **미답변 질문이면 같은 질문을 재낭독**한다(이탈 직전 질문은 못 들었을 가능성이 크다). 재낭독은 발화만 하고 **재커밋하지 않는다**(이미 transcript에 있는 질문 — 중복 방지, 번호 미소모). 마지막 발화가 답변이면 일반 턴 파이프라인(판단→생성)으로 다음 질문을 진행한다.
  - **재입장 vs 창 만료의 경합은 종료 상태 머신이 수렴한다**: 창 만료는 `begin_closing` 시도(전이 승자만 부수효과 — 기존 원자성 재사용)이고, 재입장 처리는 종료 국면 진입 전(`RUNNING`·`WAITING_FINAL_ANSWER`)에만 유효하다. 만료 전이가 이긴 뒤의 재입장은 종료 중인 세션을 관측할 뿐이다(first-wins — 경계 경합의 사용자 불운은 감수). 반복 disconnect/connect도 같은 규칙의 반복이다 — 이탈마다 epoch 증가·deadline 기록, 재입장마다 deadline 삭제·앵커 재실행.
- **창 소진 시 종료 수렴(시간 기준 이원화 — Overview 확정)**:
  - **시간이 남은 경우**: 새 종료 원인 `RECONNECT_TIMEOUT`(EndCause 확장 — enum 값 확정)으로 종료 국면에 진입한다 — 종료 표식 기록(기존 `CLOSING` 진입 부수효과 재사용) → **클로징 발화 생략**(청자 없음) → **flush 생략** → 리포트 발행 생략 → 룸 삭제(bounded retry — 기존 재사용) → 잡 종료. `room_finished` + 행 없음으로 Spring이 `ABORTED` 전이한다(기존 매핑 그대로). 표식이 남으므로 룸 삭제까지 실패한 최악 경로에서도 Spring 판별 ②가 재디스패치를 막는다.
  - **Redis 사본은 purge하지 않는다**: "purge ⇔ flush 성공" 불변식(interview-end.md §4)을 유지한다 — 창 소진 경로의 사본·세션 메타는 TTL로 소멸한다(수동 복구 여지 겸용).
  - **빈 룸 empty timeout 방임(대안 기각)**: agent가 룸을 남기고 퇴장하면 수렴이 느리고, `participant_left(agent)` 해석·판별 경로 의존이 늘어난다 — 직접 룸 삭제가 빠르고 결정적이며 기존 종료 시퀀스를 재사용한다.
  - **창 도중 hard 시한 선소진**: 시간 소진이 창 소진보다 먼저 오면 **정상 종료로 수렴한다** — `HARD_TIMEOUT` 종료 국면에 진입하되 청자가 없으므로 클로징 발화만 생략하고, flush·리포트 발행·룸 삭제는 정상 수행한다 → 행 있음 → `ENDED`. 사용자는 재입장하지 못했어도 진행된 면접의 리포트를 받는다.

### 실행 조건

- 본론 턴 파이프라인·종료 상태 머신(interview-end.md §1·§3) 위에서 동작 — 창 소진·재개는 기존 종료 수렴점·발화 경로를 재사용한다.
- 창 값·재개 안내 문구는 `agent/src/config.py` 상수.
- Spring의 `INTERRUPTED`·복귀 전이·재입장 토큰은 백엔드 스토리 병행(Overview 완료 조건 목록) — 연동 전에는 로컬(lk dispatch + 참가자 수동 퇴장·재입장)로 agent 동작만 검증한다.

### 검증 기준

- candidate 이탈 시 세션이 유지되고 재연결 deadline이 절대 시각으로 기록되며, 이탈 시점에 진행 중이던 질문 생성·발화가 폐기되는지 확인(단위 — 주입 가능한 가짜 시계·이벤트).
- **이탈 전에 시작된 입력의 완료가 커밋되지 않는지**(부재 중 도착·재입장 후 지연 도착·이전 완료가 끝내 미도착인 경합 픽스처 — 발화 시작 시각 대조), 재입장 후 시작된 turn은 정상 커밋되는지, 시작 시각 미제공 시 재실 검사로 폴백하는지 확인(단위).
- 창 내 재입장 시 deadline이 삭제되고, 재개 안내(고정 문구·무커밋) 후 앵커 규칙(미답변 질문 재낭독·무커밋·번호 미소모 / 답변이 마지막이면 일반 파이프라인)이 적용되는지 확인(단위).
- **identity 불일치 참가자 입장이 재개로 처리되지 않고**(로그만), identity 일치 재입장만 재개하는지, 두 참가자 동시 입장 시 일치자만 candidate로 처리되는지 확인(단위).
- **재입장과 창 만료를 동시에 발생시키는 경합 픽스처**에서 승자가 정확히 하나이고(재개 또는 종료 수렴), 부수효과가 1회만 실행되는지 확인(단위).
- 창 소진(시간 남음) 시 표식 기록·클로징 생략·flush 생략·룸 삭제·잡 종료가 이 순서로 실행되고 Redis 사본이 purge되지 않는지 확인(단위).
- 창 도중 hard 선소진 시 클로징 생략 외 정상 종료 시퀀스(flush·발행·룸 삭제)가 수행되는지 확인(단위).
- 창 동안 시계가 계속 흘러, 재입장 후 남은 시간이 이탈 전 + 부재 시간만큼 줄어 있는지 확인(단위 — 가짜 시계).
- 반복 이탈·재입장 픽스처에서 이탈마다 새 deadline이 기록되고 재입장마다 삭제되는지 확인(단위).
- 실환경: dev 모드 + lk dispatch로 입장 후 참가자 퇴장·재입장 → 면접이 이어지는지, 퇴장 후 방치 → 창 소진 종료를 확인(음성 통합 — 수동 절차 문서화).

### 성능 요구사항

- 창 타이머는 세션당 task 1개. 이탈·재입장 관측은 이벤트 기반 — 폴링 없음. deadline 기록은 이탈당 Redis 쓰기 1회.

### 인터페이스 요구사항

- 입력: candidate 이탈·재입장 이벤트(`participant_disconnected`/`participant_connected` + identity), 재연결 창 값(config).
- 출력: 재개 안내·재낭독 발화, 재연결 deadline(세션 메타 — §2), 종료 수렴(기존 종료 상태 머신 — 새 원인 추가).

### 제약사항

- 세션 상태 전이는 실행하지 않는다(Spring 단일 소스) — candidate 이탈·복귀의 `INTERRUPTED`/`ACTIVE` 전이는 Spring 몫이고, agent 발 신호는 여전히 `room_finished`뿐이다.
- 창 값·창 정책을 metadata로 받지 않는다 — 디스패치 metadata 4필드 계약 불변(§2와 공유).

### 기타 요구사항

- 이탈·재입장·창 소진·입력 경계 폐기 건수는 sessionId와 함께 운영 로그에 남긴다(개인정보 아님 — 관측·튜닝 재료). 부재 구간 길이도 기록한다.

## 2. 면접 상태 복원

### 설명

agent 프로세스가 소실돼도 면접이 끝나지 않게 한다 — Spring이 유예 내 재디스패치한 새 잡이, agent 소유 Redis 상태로 "그 면접"을 이어간다.

- **세션 메타의 내구 저장**: 복원 재료를 세션 메타 해시 하나에 모은다 — 키 `interview:{sessionId}:meta`, TTL은 transcript 사본과 동일 원칙(86400초, 쓰기 시 갱신). 필드 —

| 필드 | 기록 시점 | 기록 방식 | 값 |
| --- | --- | --- | --- |
| `startedAt` | candidate 최초 입장 관측(면접 시계 `start()`) 직후 | `HSETNX` — 재디스패치·중복 기록이 원래 시작 시각을 덮어쓰지 못한다 | UTC ISO-8601(초 단위, `Z`) |
| `candidateIdentity` | 최초 입장 관측 시 | `HSETNX` | participant identity 원문 |
| `reconnectDeadline` | 이탈 관측 시(§1) | `HSET`(이탈마다 갱신), 재입장 시 `HDEL` | UTC ISO-8601(초 단위, `Z`) |

  **최초 초기화는 원자 실행이다**: `startedAt`·`candidateIdentity`는 같은 관측점(최초 입장)에서 생기므로 EXPIRE와 함께 단일 트랜잭션(MULTI — transcript writer의 RPUSH+EXPIRE와 같은 패턴)으로 기록해, 한 필드만 남는 부분 상태를 구조적으로 제거한다. 이후의 모든 메타 쓰기도 쓰기+EXPIRE를 원자 실행한다 — Redis hash 쓰기 자체는 TTL을 만들지도 갱신하지도 않는다. 기록 실패는 경고 후 면접 계속(best-effort) — 복원은 재해 복구 층위지 면접 진행의 전제가 아니다. 유실 시의 처리는 아래 폴백 층위가 흡수한다. **방어 폴백(fail-closed)**: 그럼에도 `candidateIdentity`만 유실된 복원 세션은(원자 초기화 이후로는 오염 한정) **재개하지 않는다** — 참가자 수와 무관하게 즉시 §1 창 소진과 동일하게 종료 수렴한다(시간 기준 이원화 적용). 인원수·위치 기반 자동 채택은 두지 않는다 — "최초 identity 고정" 원칙을 폴백이 우회하면(재입장 전에 들어온 다른 참가자를 candidate로 고정, 진짜 candidate는 이후 불일치로 무시) 원칙의 존재 이유가 사라진다. Spring 조회로 identity를 복구하는 대안은 새 HTTP 결합이라 기각 — 오염 한정 경로에 비례하지 않는다.
- **정상 종료 시 세션 메타도 함께 정리한다(확정)**: flush 성공 후 Redis 정리(purge — interview-end.md §4)의 대상에 세션 메타를 포함한다 — `candidateIdentity` 등 개인 식별 재료의 보존을 TTL 만료보다 앞당겨 끝낸다(개인정보 최소 보존). 비정상 경로는 기존 불변식(purge ⇔ flush 성공) 그대로 — 메타·사본 모두 TTL로 소멸한다. **`owner` 키(아래 동시 잡 방어)는 purge 대상이 아니다** — 종료 시퀀스상 purge 뒤에 오는 룸 삭제까지 가드로 유효해야 한다(메타와 함께 지우면 정상 잡이 purge 직후 자기 룸 삭제를 스스로 차단한다).
- **신규/복원 판별 = agent 소유 Redis 상태 존재(확정)**: 디스패치 metadata 4필드(sessionId·interviewType·position·resumeContext)는 확정 크로스 레포 계약이라 재디스패치 구분 필드를 추가하지 않는다. 잡 시작 시 sessionId로 Redis를 조회해 판별한다 —

| 관측 | 판별 | 처리 |
| --- | --- | --- |
| 종료 표식 있음 | 이미 종료 국면에 진입했던 세션(Spring 계약상 재디스패치 대상 아님) | 방어적 즉시 종료 — 아무 상태도 훼손하지 않고 잡만 종료(룸 삭제·표식 갱신 없음) |
| `startedAt` 있음 | 복원 대상 | 경과 시간 역산 + 대화 사본 재구성 + 종료 국면 유도 → 재개(아래) |
| `startedAt` 없음 + transcript 있음 | 복원 대상(시작 시각만 유실) | **첫 발화 `spokenAt`으로 시작 시각을 근사 복원**(시작 ≤ 첫 발화 시각이므로 오차는 수 초, 사용자에게 유리한 방향) → 재개 |
| 둘 다 없음 | **신규 세션과 구조적으로 구분 불가** | 새 면접으로 시작 — 수용 리스크(아래) |

  - **둘 다 유실 폴백 = 새 면접(확정)**: metadata 불변 계약 아래에서 유일한 선택지다. 시간 예산이 리셋되는 리스크는 연습 면접의 재면접 허용 위험 성향(ADR-E3-10)과 일관하며, Spring stale 회수(45분)가 상한 안전망이다. 발생 조건은 Redis 유실(장애) 또는 최초 입장 직후 메타 기록 완료 전 소실로 한정된다 — 후자는 면접 극초반(수 초)이라 새 면접 시작의 실질 손실이 없다. **수용 리스크로 확정**.
- **경과 시간 복원**: `경과 = 현재 벽시계 − startedAt`으로 역산해 면접 시계에 주입한다(단조 시계 기준점 보정). 끊김·재디스패치 지연 시간이 모두 경과에 포함된다 — "끊김 중에도 시계는 계속 흐른다"와 일관. 예: 20분 시점 소실 + 2분 뒤 복원 → 남은 시간 약 8분. **손상 값 방어**: `startedAt`이 파싱 불가면 "유실"로 취급해 다음 폴백 층위(첫 발화 근사)로 내려가고, 미래 시각이면(벽시계 역행·오염) 경과를 0으로 clamp하고 경고를 남긴다 — 음수 경과로 면접이 길어지는 방향의 오류만 차단한다(hard 시한 초과 방향은 기존 규칙이 수렴).
- **대화 사본 재구성(관대한 경로)**: `interview:{sessionId}:transcript` List 전체를 읽어 메모리 대화 로그를 재구성한다. Redis 사본은 best-effort(드롭 gap 허용)이므로 재구성은 불변식을 강제하지 않는 관대한 경로로 하되, 규칙을 명시한다 —
  - **드롭은 파싱 불가(스키마 위반) 항목만** 한다(건수만 로그). **참조 무결성 위반은 드롭하지 않는다** — 루트 질문이 유실된 꼬리질문, 질문이 유실된 답변도 보존한다. 재구성 로그의 용도는 LLM 컨텍스트 재료와 flush 원본이고, 구조 조회(줄기 등)는 부분 결과를 감수한다 — 내용을 버리는 것보다 낫다(연쇄 드롭 없음).
  - **루트가 유실된 줄기에는 꼬리질문을 이어붙이지 않는다**: 재구성 로그의 현재 줄기 루트가 실존 질문이 아니면(orphan 줄기), 재개 후 첫 판단을 `NEXT_TOPIC`(마무리 단계면 `FINAL_QUESTION`)으로 강제한다 — 보존된 orphan에 `FOLLOW_UP`을 커밋하면 현행 불변식 검사("parent는 존재하는 줄기 루트")에서 실패하므로, 기존 코드 우선 결정 패턴으로 원천 차단한다.
  - **다음 질문 번호 = 재구성 로그에서 관측된 최대 `questionNumber` + 1**. 이후 신규 발화부터는 기존 불변식이 그대로 적용된다.
  - **앵커·종료 국면 유도의 "마지막 발화" = 드롭 제외 후 재구성 리스트의 마지막 항목**.
  - **flush "메모리 완전본" 원칙의 명시적 예외**: 복원 세션의 메모리 로그는 재구성본이라 pre-crash 구간에 gap이 있을 수 있다. 복원 자체가 최선 노력이므로 감수하고, 이후 정상 종료 시 flush는 이 재구성본 + 신규 발화를 원본으로 한다(interview-end.md §4에 대한 이 문서의 예외 — 소비자 영향 없음: 스키마는 동일).
  - transcript만 유실되고 `startedAt`이 남은 경우: **빈 로그 = 신규와 같은 진행 경로**다 — 남은 시간만 복원하고, 초기 질문 선택·발화를 다시 수행한다(아래).
- **종료 국면 복원 = transcript에서 유도(확정 — 별도 저장 없음)**: 시계·대화만으로는 종료 상태 머신(`EndPhase`)을 복원할 수 없다 — 마지막 발화 기준 판별표로 유도한다. 별도 상태 키를 두지 않는 이유: 유도 가능한 상태의 이중 저장은 불일치 창만 만든다(표식이 이미 "종료 국면 진입"의 내구 증거다).

| 재구성 로그의 마지막 발화 | 유도 국면 | 처리 |
| --- | --- | --- |
| `closing` 발화 | 종료 시퀀스 미완(클로징까지 재생됐으나 flush 전 소실 — 표식 기록 실패와 겹친 경로) | **종료 표식을 원인 `RECOVERED_CLOSING`(EndCause 확장 — enum 값 확정. 원래 원인은 transcript만으로 복구 불가)으로 먼저 재기록**한 뒤, **클로징 재발화 없이 종료 시퀀스를 재개**한다(flush → 정리 → 발행 → 룸 삭제) → 행 기록 → `ENDED`. candidate 입장 대기 불요. 표식 재기록이 없으면 복원 flush까지 실패한 경로가 다시 "행·표식 둘 다 없음"이 되어 판별 ③ 재디스패치가 반복된다 — 이 경로는 표식 기록 실패로만 진입하므로 재기록이 루프 차단이다. Spring 판별은 표식의 존재만 보므로(cause 값은 관측 재료 — interview-end.md §3) 신규 값이 판별 계약을 바꾸지 않는다 |
| `final` 질문 + 답변 있음 | 마지막 답변까지 완료 | `CLOSING` 진입 — 클로징 발화(candidate 부재 시 생략) 후 종료 시퀀스 |
| `final` 질문 + 답변 없음 | `WAITING_FINAL_ANSWER` | 재개 후 앵커 = **final 질문 재낭독**, 답변 1회 커밋 → `CLOSING`(기존 커밋 정책 그대로) |
| 그 외 | `RUNNING` | 재개 후 §1 앵커 규칙(미답변 질문 재낭독 / 일반 파이프라인) |

  잔여 리스크: gap으로 `closing`·`final` 발화 자체가 사본에서 유실되면 국면을 과소 복원한다(본론으로 재개) — 표식이 남는 정상 경로에서는 판별표 1행(방어 종료)이 먼저 걸리므로, 표식 기록 실패와 사본 gap이 **동시에** 난 경우로 한정된다. 감수하고 로그로 관측한다.
- **복원 후 진행**:
  - **재구성 로그가 비어 있지 않으면** 초기 질문 선택(LLM 호출)을 건너뛰고, candidate 입장 관측 시 **재개 안내 발화 → 유도 국면별 앵커(위 표)**로 재개한다.
  - **재구성 로그가 비어 있으면 초기 질문 경로를 다시 탄다**(선택 LLM 호출 + 초기 질문 발화 — 신규와 동일). 초기 질문 없이는 파이프라인이 시작될 수 없다 — 현행 구조는 질문이 커밋되기 전의 발화를 답변으로 받지 않고, 답변 커밋이 있어야 다음 질문 생성이 시작된다(빈 로그 + 초기 질문 생략은 진행 불능이다).
  - **복원 잡의 candidate 입장 대기 = 잔여 재연결 창**: 신규 잡의 입장 대기(300초)가 아니라 **`min(reconnectDeadline, hard 시한) − now`** 를 적용한다 — 끊김은 이탈 시점에 이미 시작됐고, 복원 잡의 대기는 그 창의 **연속**이다(재디스패치가 창을 3분씩 다시 부여하지 않는다 — §1 deadline 내구화의 목적). `reconnectDeadline`이 없으면(candidate 재실 중 agent만 소실 — 이탈 관측자가 없던 경우): 입장해 있으면 즉시 재개하고, 부재면 **그 시점부터 새 창**을 시작해 deadline을 기록한다(부재 시작을 관측할 주체가 없었으므로 복원 시점을 관측점으로 삼는다 — 사용자에게 유리한 방향의 근사). 대기 소진 시 §1 창 소진과 동일하게 수렴한다(시간 기준 이원화).
  - **복원 시점에 hard 이미 소진**: 면접은 사실상 완주됐다 — 즉시 정상 종료로 수렴한다(시간 소진형). candidate가 있으면 시간 소진형 클로징을 발화하고, 없으면 생략한다. flush → 행 기록 → `ENDED` — 사용자는 리포트를 받는다.
- **동시 잡 방어(이중 디스패치)**: 같은 세션에 두 잡이 겹치는 split-brain에 대한 **안전 보장은 Spring의 활성 dispatch 단일성 계약(Overview 조건 5) 하나다(확정)**. agent 측 `owner` 검사는 **관측·완화 계층으로만 둔다** —
  - **`owner`는 세션 메타 밖의 별도 키다** — `interview:{sessionId}:owner`(값 = 잡 식별자, TTL 동일 원칙). 복원 재료가 아니라 종결 단계 가드라서 메타와 수명이 다르다 — 메타는 flush 성공 시 purge되지만 owner는 그 뒤의 룸 삭제까지 유효해야 한다. 잡 시작 시 `SET`(last-wins)하고, 종결 단계(종료 표식 기록·flush·purge·룸 삭제) 직전에 확인한다 — **다른 잡의 식별자가 관측될 때만** 해당 단계를 생략하고 잡만 종료하며(위반 관측 로그), **부재는 통과**다(인수자는 반드시 자기 식별자를 기록하므로 부재 = 인수 관측 없음). 잡 종료 직전 자기 소유면 `DEL`한다(best-effort — 실패 시 TTL 소멸).
  - **이 검사는 경쟁을 막지 못한다**: 확인과 실행 사이가 원자적이지 않아(TOCTOU — 확인 직후 신 잡이 `owner`를 덮고 구 잡이 실행할 수 있다) 경쟁 창을 좁힐 뿐이다. fencing token으로 원자화하려 해도 flush는 Postgres, 룸 삭제는 LiveKit API라 Redis 기반 보호가 닿지 않는다 — 전면 fencing은 노출 범위에 비례하지 않아 채택하지 않는다(구 잡은 룸 연결을 잃어 발화 불가 → TTS 실패 → 오류 종료 경로 — 구조적으로 flush 없음).
  - 잔존 구(舊) 잡의 transcript append 오염은 사본의 기존 best-effort 클래스(gap·중복 감수)로 흡수한다.
- **연쇄 성립(교차 시나리오)**: 재연결 창 도중 agent가 소실되면 — 창 동안 표식·행 모두 없으므로 Spring 판별 ③(`AGENT_LOST`) → 유예 내 재디스패치 → 이 기능이 잔여 창부터 복원한다. **복원은 sessionId 기준이고 room과 무관하다** — 재디스패치가 어느 룸에서 일어나든 성립한다(룸 재사용·재생성은 백엔드 몫). 빈 룸의 empty timeout·`room_finished`와 재디스패치의 경쟁은 Spring terminal no-op 가드·판별 계약이 수렴한다(백엔드 스토리 완료 조건 — 이 문서는 agent 측 보장만 정의).

### 실행 조건

- 잡 시작 시 Redis 조회(메타 HGETALL·표식 GET·transcript LRANGE)가 추가된다 — sessionId 있는 잡의 Redis 미구성 fail-fast(interview-end.md §3)는 그대로 전제된다.
- 복원 검증은 로컬 Redis로 가능(dev 모드 + lk dispatch → 잡 강제 종료 → 동일 metadata 재디스패치 → 복원 확인 — 수동 절차 문서화).

### 검증 기준

- 세션 메타가 정의된 시점·방식(`HSETNX`/`HSET`/`HDEL`)대로 기록되고 기존 `startedAt`·`candidateIdentity`가 보존되는지, **최초 초기화가 두 필드 + EXPIRE를 단일 원자 실행으로 기록하고 모든 메타 쓰기 후 TTL이 살아있는지**, 기록 실패 시 면접이 계속되는지 확인(단위 — 로컬 Redis 없으면 skip).
- `candidateIdentity`만 유실된 복원 픽스처에서 참가자 수(0·1·복수)와 무관하게 재개 없이 종료 수렴(fail-closed — 시간 기준 이원화 적용)하는지 확인(단위).
- flush 성공 경로에서 transcript와 함께 세션 메타가 삭제되고, 비정상 경로(창 소진 등)에서는 둘 다 보존(TTL 소멸)되는지 확인(단위 — 로컬 Redis 없으면 skip).
- **정상 종료 경로에서 meta purge 이후의 룸 삭제가 owner 가드에 차단되지 않는지**(별도 키 — purge 무관), owner 부재 시 종결 단계가 통과되고 다른 잡 식별자 관측 시에만 생략되는지 확인(단위).
- 판별 표의 4경로가 각각 올바르게 동작하는지 확인(단위 — Redis 스텁): 표식 → 방어 종료(상태 무훼손), `startedAt` → 역산 복원, `startedAt` 유실 + transcript → 첫 발화 `spokenAt` 근사, 둘 다 없음 → 신규 경로.
- 경과 역산: 20분 시점 저장 + 2분 뒤 복원 픽스처에서 남은 시간이 약 8분인지, `startedAt` 파싱 불가 → 근사 폴백·미래 시각 → 경과 0 clamp가 동작하는지 확인(단위 — 가짜 벽시계·단조 시계).
- 재구성 규칙 확인(단위): 파싱 불가 항목만 드롭(건수 로그), 참조 무결성 위반 발화 보존(연쇄 드롭 없음), 다음 질문 번호 = 최대 관측 번호 + 1, 재구성 후 신규 발화 커밋이 기존 불변식대로 동작.
- **종료 국면 유도 판별표의 4행이 각각 동작하는지** 확인(단위): `closing` → **원인 `RECOVERED_CLOSING`으로 종료 표식 재기록 후** 재발화 없이 종료 시퀀스 재개(flush → 행 기록), `final`+답변 → `CLOSING` 직행, `final` 미답변 → `WAITING_FINAL_ANSWER` + final 재낭독 + 답변 1회 커밋 후 클로징, 그 외 → `RUNNING` + §1 앵커.
- **orphan 줄기 픽스처**(루트 유실 + 꼬리질문 잔존)에서 재개 후 첫 판단이 `NEXT_TOPIC`(마무리 단계면 `FINAL_QUESTION`)으로 강제되어 `FOLLOW_UP` 커밋 실패가 발생하지 않는지 확인(단위).
- **빈 재구성 로그 복원이 초기 질문 선택·발화를 다시 수행**하고 이후 파이프라인이 정상 진행되는지 확인(단위).
- 복원 잡의 입장 대기가 `min(reconnectDeadline, hard 시한) − now`를 쓰고, deadline 부재 시(candidate 부재) 새 창을 기록하며, 소진 시 §1과 동일 수렴하는지 확인(단위).
- 복원 시점 hard 소진 픽스처에서 즉시 정상 종료(flush 포함, candidate 부재 시 클로징 생략)로 수렴하는지 확인(단위).
- **동시 잡 픽스처(완화 계층 검증)**: 후발 잡이 `owner`를 차지한 뒤 선발 잡의 종결 단계가 소유권 확인으로 생략·로그되는지 확인(단위 — Redis 스텁). 이 테스트는 완화 계층의 동작 검증이다 — TOCTOU 창의 부재를 보장하지 않으며, 동시 잡 자체의 부재는 Spring dispatch 단일성 계약(Overview 5)이 담당한다.
- 실환경: 잡 강제 종료 후 동일 metadata 재디스패치 → 대화 맥락·남은 시간이 유지된 재개를 확인(음성 통합 — 수동 절차 문서화).

### 성능 요구사항

- 복원은 잡 시작 시 1회의 Redis 조회(HGETALL·GET·LRANGE)다 — 30분 대화 사본은 수십 KB 수준으로 지연 무시 가능. 소유권 검사는 종결 단계당 GET 1회.

### 인터페이스 요구사항

- 입력: 디스패치 metadata(기존 4필드 그대로), Redis 키 — `interview:{sessionId}:meta`(신규 해시 — `startedAt`·`candidateIdentity`·`reconnectDeadline`), `interview:{sessionId}:owner`(신규 — 종결 단계 가드, purge 비대상), `interview:{sessionId}:transcript`(기존), `interview:{sessionId}:termination`(기존 — 조회만).
- 출력: 복원된 면접 시계·대화 로그·종료 국면, 재개 안내·재낭독 발화.

### 제약사항

- **디스패치 metadata 4필드 계약 불변(확정)** — 재디스패치 구분 필드를 추가하지 않는다. 신규/복원 판별은 agent 소유 저장소의 상태 존재로만 한다.
- Spring 소유 저장소에는 쓰지 않는다(쓰기 권한 경계 = 소유권 경계) — 신규 키도 agent 소유 Redis 네임스페이스(`interview:{sessionId}:*`)에만 둔다.
- 재디스패치 실행·유예 창 관리·룸 재사용·활성 dispatch 단일성은 Spring 몫(범위 외 — Overview 계약 조건으로만 정의).

### 기타 요구사항

- 복원 발생·판별 경로·유도 국면·재구성 건수(드롭 건수 포함)·소유권 검사 결과는 sessionId와 함께 운영 로그에 남긴다(대화 내용 제외 — 기존 로그 프라이버시 원칙).
