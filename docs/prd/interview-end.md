# 면접 종료

> **User Story**: HBB1-283 — 나는 사용자로서 면접을 종료할 수 있다.
>
> **하위 이슈**: HBB1-284 [개발] 면접 시간 관리·종료 신호 개발 · HBB1-285 [개발] 마무리 판단·클로징 발화 개발 · HBB1-286 [개발] 세션 정리·퇴장 개발 · HBB1-287 [개발] transcript DB 저장 개발 · HBB1-288 [개발] 리포트 생성 요청 발행 개발

## Overview

진행 중인 면접을 정상 종료(`ENDED`)로 마무리하는 기능 영역이다. `agent/`(kkori-agent)의 LiveKit 음성 에이전트 프로세스에서 실행되며, 본론 면접 루프(`docs/prd/follow-up-question.md`)에 시간 축을 더해 마무리 단계 진입 → 클로징 발화 → 종료 시퀀스(전사 저장·리포트 요청·퇴장)를 담당한다.

핵심 데이터 흐름: 경과 시간(코드 관리) → **soft**(마무리 단계): Orchestrator에 마무리 신호·**남은 시간** 주입 → `FINAL_QUESTION`(마지막 질문 → 마지막 답변 → 클로징) 또는 `END`(즉시 클로징) 판단 / **hard**(시간 명백 초과): 코드 강제 클로징 / **사용자 종료**: Spring발 종료 신호 수신 — 모든 경로가 **단일 종료 상태 전이**로 수렴 → 클로징 발화(사유별 검수 고정 문구, 끼어들기 불가) → 종료 시퀀스: 대화 로그 확정(신규 커밋 차단·Redis writer 종료) → transcript DB flush(메모리 완전본 → jsonb 1행) → Redis 사본 정리 → 리포트 생성 요청 발행(Redis Stream) → 룸 삭제(bounded retry) → 잡 종료 → LiveKit `room_finished` webhook → Spring이 `ENDED` 전이.

주체 정리: **세션 상태의 단일 소스는 Spring**이다(모든 상태 전이는 Spring 실행 — 드래프트 상태 머신 계승). agent는 상태를 바꾸지 않고, "면접을 끝낸다"는 도메인 행위(클로징·flush·리포트 발행·룸 정리)를 실행한 뒤 **룸 종료(`room_finished`)로 신호**한다. 사용자 명시 종료는 Spring이 API로 수신해 서버 API data 메시지(`SendData`)로 agent에 전달한다(§3 — 확정, 세부 계약만 미확정).

**범위**: `interviewType=THIRTY_MIN`(30분, 이력서 기반)만 다룬다. 다음은 별도 스토리 범위로 이 문서에서 다루지 않는다 — 5분 CS 유형, 재연결·Agent 복원(`INTERRUPTED`/`AGENT_LOST` — 비정상 경로는 "flush 생략" 원칙만 계승), Spring의 세션 API·상태 머신·webhook 구현(agent와의 계약만 정의), 리포트 생성 자체(worker — 이 문서는 요청 발행까지), 탈퇴·파기(E1), 프론트의 종료 UI·리포트 대기 화면.

### 기능 요구사항

| No. | Function | Description |

| 1 | 면접 시간 관리·종료 신호 | 코드가 면접 경과 시간을 관리하고, soft(마무리 단계 진입)·hard(강제 종료)·외부 종료 신호를 단일 종료 상태 머신으로 수렴 |

## 1. 면접 시간 관리·종료 신호

### 설명

면접의 시간 축은 전부 코드가 관리한다 — LLM은 시간을 알지 못하고, 코드가 주입한 신호(마무리 단계)에만 반응한다.

- **기준 시각(면접 시작) = candidate 입장 시각 (확정)**: agent가 candidate 입장을 관측한 시각(참가자 대기 완료 시점)을 면접 시작으로 본다 — 사용자가 룸에 들어온 순간부터가 면접이며, 사용자 체감·Spring의 세션 타임라인과 어긋나지 않는다. 입장 후 초기 질문 준비(선택 LLM 호출) 지연도 면접 시간에 포함된다(수 초 수준 — 감수). 경과 계산은 단조 시계(monotonic) 기준으로 하여 벽시계 조정에 영향받지 않는다. **끊김 중에도 시계는 계속 흐른다(확정 — 리뷰 질문 반영)**: 재연결(INTERRUPTED) 동안 시계를 멈추지 않는다 — 재연결 창(3분)이 짧아 잠식이 제한적이고, 멈추면 반복 끊김으로 세션 수명이 비결정적이 되며, 연습 면접의 재면접 가능 위험 성향(ADR-E3-10)과 일관된다. 단조 시계는 프로세스 로컬이므로 **재dispatch 시 경과 시간 복원(시작 시각의 내구 저장)은 Agent 복원 스토리 과제**다.
- **면접 총 시간**: `interviewType`별 코드 상수(`THIRTY_MIN` = 30분). 유형 추가 시 상수만 추가한다.
- **soft 신호(마무리 단계 진입)**: 남은 시간이 임계치(5분 — 기본값 확정, 실측 조정 여지) 이하가 된 이후 시작되는 턴부터, 코드가 Orchestrator 프롬프트에 마무리 단계 신호와 **남은 시간(분 단위 근사 — 예: "약 4분")**을 주입하고 마무리 액션(`FINAL_QUESTION`·`END`)을 허용한다(§2). 시간은 **판단 재료로만** 전달한다 — 시간의 계산·강제 권한은 코드에 남는다(과도한 정밀도는 주입하지 않는다). 시간 확인은 타이머 이벤트가 아니라 **턴 경계(판단 직전)**에서 한다 — 신호는 다음 판단에 반영되면 충분하고, 진행 중인 발화·답변을 시간 이벤트가 끊지 않는다.
- **hard 강제(안전망)**: 예정 종료 시각을 유예(3분 — 기본값 확정, 실측 조정 여지)까지 초과하면, 타이머 task가 LLM 판단·턴 진행과 무관하게 종료 상태를 `CLOSING`으로 전이시키고 클로징 발화를 시작한다. 재생 중인 발화가 있으면 완료를 기다린 뒤 클로징한다(발화는 끼어들기 불가 — 선행 PRD 계승). candidate가 답변 중이거나 **마지막 질문 단계가 진행 중이어도** 클로징으로 직행한다 — hard는 정상 경로가 아니라 soft 실패 시의 안전망이며, 정상적으로는 soft 단계에서 Orchestrator가 먼저 마무리를 판단한다.
- **종료 상태 머신(단일 수렴점)**: 종료는 boolean 래치가 아니라 **전진 전용 상태**로 관리한다 — `RUNNING`(진행) → `WAITING_FINAL_ANSWER`(마지막 답변 대기 — `FINAL_QUESTION` 경로만 경유) → `CLOSING`(클로징) → `CLEANING`(종료 시퀀스 — §3) → `CLOSED`. 중복·역방향 전이는 no-op이지만, **전진 전이는 어느 상태에서든 허용**된다:
  - `FINAL_QUESTION` 확정 → `WAITING_FINAL_ANSWER`. 마지막 답변 turn 완료 → `CLOSING`.
  - `END` 확정·hard 타이머·외부 종료 신호(§3) → `CLOSING` 직행. **hard·사용자 종료는 `WAITING_FINAL_ANSWER`에서도 `CLOSING`으로 승격한다** — 마지막 답변 대기가 hard·사용자 종료를 막지 않는다(boolean 래치였다면 먼저 걸린 `FINAL_QUESTION`이 이후 신호를 no-op으로 삼켰을 것).
  - `RUNNING`을 벗어나는 전이와 함께 진행 중인 질문 생성 실행은 결과를 폐기한다(기존 turn_seq 무효화 메커니즘 재사용). 질문 생성 파이프라인은 `RUNNING`에서만 시작된다.
  - **전이 원자성·부수효과 1회 보장**: hard 타이머·외부 종료 메시지·마지막 답변 완료는 서로 다른 task에서 동시에 발생할 수 있다 — 상태 전이는 단일 lock/CAS로 원자적으로 실행하고, **전이에 성공한 신호만** 해당 상태의 진입 부수효과(클로징 시작·종료 표식 기록·종료 시퀀스 시작)를 **정확히 1회** 실행한다(두 task가 같은 `RUNNING→CLOSING`을 관측해 클로징·flush가 두 번 시작되는 경쟁 차단). **종료 원인(사유 enum)은 `CLOSING` 진입 전이에서만 원자적으로 확정**한다 — `WAITING_FINAL_ANSWER` 자체에는 원인을 두지 않는다(마무리 국면 진입 ≠ 종료 원인 확정). `CLOSING` 진입 경로가 곧 원인이다: 마지막 답변 완료 → `FINAL_QUESTION`(일반형), `END` 판단 → `LLM_END`(시간 소진형), hard 승격 → `HARD_TIMEOUT`(시간 소진형), 사용자 종료 승격 → `USER_REQUEST`(일반형). `CLOSING` 진입 경합은 first-wins로 원인을 정하고 패자 신호는 no-op. 클로징 문구 세트(§2)는 이 원인을 따른다 — 마무리 국면(`WAITING_FINAL_ANSWER`) 도중 hard가 승격해도 낡은 원인이 남지 않고 시간 소진형이 정확히 선택된다.
- **종료 국면의 답변 커밋 정책(경로별)**: transcript에 남기는 발화의 경계를 경로별로 명시한다 —
  - `WAITING_FINAL_ANSWER`: **마지막 질문 재생 성공 후 완료된 첫 user turn 1회만** 답변으로 커밋하고 `CLOSING`으로 전이한다. **상태 확인 → 답변 커밋 → `CLOSING` 전이는 같은 임계구역(lock) 안에서 실행**한다 — 상태 확인 직후 hard·사용자 종료가 먼저 `CLOSING`으로 전이하면 뒤늦은 커밋이 "CLOSING 진입 이후 커밋 금지"를 깨는 경쟁을 차단한다(전이를 선점당했으면 커밋하지 않는다).
  - `END`·hard·사용자 종료(`CLOSING` 직행): 전이 이후 완료되는 user turn은 **커밋하지 않는다** — 종료 확정 뒤의 발화(작별 인사, 종료 요청 후 발화)는 면접 내용이 아니다. hard 전이 시점에 진행 중이던 미완료 답변도 동일하게 폐기한다(완료 시점 경쟁에 따른 비결정적 커밋을 배제 — hard는 이미 +3분 초과의 예외 경로다).
  - `CLOSING` 진입 이후의 발화는 어떤 경로에서도 커밋하지 않는다.

### 실행 조건

- 본론 턴 파이프라인(follow-up-question.md 기능 1) 위에서 동작 — 시간 신호는 파이프라인의 판단 단계에 주입된다.
- 시간 상수는 `agent/src/config.py`로 구성.

### 검증 기준

- soft 임계치 진입 이후의 턴에서 Orchestrator 프롬프트에 마무리 신호·남은 시간(분 단위 근사)이 주입되고, 이전 턴에는 주입되지 않는지 확인(경계 케이스 포함, 단위 — 주입 가능한 가짜 시계로 검증).
- hard 유예 초과 시 진행 중 파이프라인 결과가 폐기되고 클로징이 발화되는지 확인(단위).
- 종료 상태가 전진 전용으로만 전이되고(중복·역방향 no-op), hard·사용자 종료가 `WAITING_FINAL_ANSWER`에서도 `CLOSING`으로 승격되는지 확인(단위).
- hard·사용자 종료·마지막 답변 완료를 동시에 발생시키는 경합 픽스처에서 상태 전이·클로징·종료 시퀀스가 정확히 1회만 실행되고, 종료 원인이 `CLOSING` 진입 전이 기준 first-wins로 확정되며, **transcript의 마지막 답변 포함 여부가 전이 승자와 일치**하는지(선점당한 커밋이 남지 않는지) 확인(단위).
- `WAITING_FINAL_ANSWER` 도중 hard·사용자 종료가 승격하면 각각 시간 소진형·일반형 클로징 문구가 선택되는지(낡은 원인 잔존 없음) 확인(단위).
- 경로별 커밋 정책 확인(단위): `WAITING_FINAL_ANSWER`에서 마지막 질문 재생 성공 후 완료된 첫 turn만 커밋되고, `CLOSING` 직행 경로(END·hard·사용자 종료)의 전이 이후 turn과 `CLOSING` 진입 이후 발화는 커밋되지 않는지.
- 위 항목은 음성 통합 전 텍스트 레벨에서 먼저 검증한다(시계·LLM 주입 가능한 구조).

### 성능 요구사항

- 시간 확인은 턴 경계의 메모리 연산 — 지연 영향 없음. hard 타이머는 세션당 task 1개.

### 인터페이스 요구사항

- 입력: candidate 입장 관측 시각(참가자 대기 완료 시점 — 기준 시각), 시간 상수(총 시간·soft 임계치·hard 유예).
- 출력: 마무리 단계 신호·남은 시간(Orchestrator 프롬프트 주입 — §2), 종료 상태(§1~§3 공유).

### 제약사항

- 시간 초과·마무리 판단 외의 종료 사유(오류 종료, candidate 이탈)는 §3의 경계 정의를 따른다 — 이 기능은 정상 종료 신호만 다룬다.

### 기타 요구사항

- 경과 시간·잔여 시간은 개인정보가 아니므로 운영 로그 기록 가능(관측·튜닝 재료).

## 2. 마무리 판단·마지막 질문·클로징 발화

### 설명

마무리 단계(soft)에서 Orchestrator가 **남은 시간을 재료로** 어떻게 끝낼지 판단하고, 마무리 국면(마지막 질문 → 마지막 답변 → 클로징, 또는 즉시 클로징)을 실행한다.

- **마무리 액션(soft 단계 한정)**: 마무리 단계의 턴에서만 Orchestrator 액션 집합을 {`FOLLOW_UP`, `FINAL_QUESTION`, `END`}로 바꾼다(스키마·프롬프트 모두 — 마무리 단계 신호·남은 시간과 함께 노출). 판단 규칙 —
  - 현재 줄기에 파고들 가치가 남았고 시간 여유가 있으면 → `FOLLOW_UP`(마지막 주제를 짧게 마무리).
  - 줄기가 소진됐고 마지막 질문을 받을 시간이 남았으면 → `FINAL_QUESTION`(마무리 국면 진입).
  - 시간이 사실상 소진됐으면 → `END`(즉시 클로징 — 시간 소진형 문구).
  - **`NEXT_TOPIC`은 허용하지 않는다** — 새 주제를 시작하기에 남은 시간이 부족하고, 어중간하게 시작된 주제는 평가 재료도 되지 못한다.
  - 시간의 권위는 코드다: LLM이 시간을 오판해도 양방향 모두 안전하다 — 여유가 있는데 `END`면 조금 일찍 끝날 뿐이고, 종료를 미루는 오판은 hard 안전망(§1)이 수렴한다.
- **마지막 질문(`FINAL_QUESTION`) = 검수된 고정 목록**: "마지막으로 하고 싶은 말씀 있으신가요?" 계열의 검수 문구 목록(코드 상수, 2~3개 랜덤)에서 발화한다 — 초기 질문·클로징과 같은 원칙(LLM 텍스트의 발화 유입 차단). **역질문 유도형("궁금한 점 있으신가요?")은 목록에서 제외한다** — candidate의 질문에 agent가 답변할 능력(회사 정보·답변 파이프라인)이 없는 상황을 구조적으로 만들지 않는다.
  - **답변은 1회만 받는다**: 마지막 질문 재생 성공 후 완료된 첫 user turn만 마지막 답변으로 커밋하고(§1 커밋 정책), 코드가 꼬리질문 없이 클로징을 강제한다 — 마무리 국면이 본론으로 회귀하지 않는다.
  - **발화 객체**: 마지막 질문도 질문이다 — `questionNumber` 부여(parent=self 루트), `questionType="final"`로 커밋하고, 마지막 답변이 번호를 승계한다. 마지막 어필도 transcript에 남아 리포트 평가 재료가 된다.
  - **무응답 엣지**: 답변이 없으면 turn이 완료되지 않아 클로징이 나가지 않는다 — hard 안전망이 수렴한다. 별도의 짧은 무응답 대기 상한을 둘지는 **[미확정 — 실측 관찰 후]**.
  - **재생 실패**: 1회 재시도, 소진되면 커밋 없이 클로징으로 진행한다.
- **클로징 발화 = 사유별 검수 고정 문구 (확정)**: 클로징은 코드 상수의 검수 문구 목록에서 발화한다(LLM 생성 없음 — 마지막 인상을 남기는 발화에 품질 리스크·지연을 더하지 않는다. 개인화된 마무리 코멘트는 리포트의 역할). 문구는 **종료 사유별 세트**로 나눈다 —

| 세트 | 사용 경로 | 예 |
| --- | --- | --- |
| 일반형 | `FINAL_QUESTION` 경유·사용자 종료 | "오늘 면접은 여기까지입니다. 수고하셨습니다." |
| 시간 소진형 | `END` 판단·hard 강제 | "시간이 다 되어서 면접은 여기까지 진행하겠습니다. 수고하셨습니다." |

  리포트 준비 안내 포함 여부는 프론트 UX와 협의 **[미확정]**. 사용자 종료에서 클로징을 생략(즉시 정리)할지도 프론트 UX와 협의 **[미확정 — 기본은 일반형 발화]**.
- **강제·폴백의 수렴**: 마무리 단계의 줄기 상한 도달(코드 강제)·Orchestrator 폴백(구조화 실패·미정의 값·호출 실패)은 **`FINAL_QUESTION`으로 수렴**한다 — 마지막 질문은 직전 답변 평가에 의존하지 않아 항상 안전하고, 즉시 클로징보다 정상적인 마무리 국면을 우선한다. 비마무리 단계에서 `FINAL_QUESTION`·`END`가 반환되면(비노출이라 원칙상 불가 — 방어) `NEXT_TOPIC`으로 강등한다.
- **클로징 발화 객체**: 클로징도 transcript에 적재한다(실제 들은 발화). `speaker=INTERVIEWER`, `questionType="closing"`, `content`, `spokenAt`(재생 시작 관측 시각 — 기존 규칙)으로 기록하되, **질문 번호는 부여하지 않는다**(`questionNumber`·`parentQuestionNumber` 생략). 판별 규칙: **질문이면 번호 있음(`final` 포함), 인사면 없음**. `END`가 Orchestrator 판단이면 `reason`을 기록한다(코드 강제·외부 종료에는 없음 — 기존 reason 존재 규칙과 일관).
- **클로징 재생 실패**: 끼어들기 불가로 재생하고, 실패 시 같은 문구로 1회 재시도한다(질문과 동일). 재시도 소진 시 질문과 달리 잡을 종료하지 않고 **클로징 없이 종료 시퀀스를 계속한다** — 이미 종료 국면이므로 침묵 방치가 아니며, 이 시점의 최우선 과제는 발화가 아니라 flush다. 클로징이 재생되지 않았으므로 발화 객체도 커밋하지 않는다.

### 실행 조건

- 기능 1의 마무리 단계 신호(남은 시간 포함)·종료 상태 머신 위에서 동작.
- Orchestrator 스키마·프롬프트 확장은 기존 구조화 출력(`response_format`) 방식을 계승.

### 검증 기준

- 마무리 단계 턴의 프롬프트·스키마에 `FINAL_QUESTION`·`END`와 남은 시간이 노출되고 `NEXT_TOPIC`이 제거되는지, 비마무리 단계는 기존 집합 그대로인지 확인(단위 — 프롬프트 조립 검증).
- 비마무리 단계에서 `FINAL_QUESTION`·`END` 반환 시 `NEXT_TOPIC` 강등을 확인(단위).
- 마무리 단계의 줄기 상한 도달·Orchestrator 폴백이 `FINAL_QUESTION`으로 수렴하는지 확인(단위).
- 마지막 질문·클로징이 검수 목록 원문과 정확히 일치하게 발화되는지 확인(단위 — 목록 밖 텍스트의 발화 유입 불가).
- 마지막 질문 발화 객체(`questionType="final"`, 번호 부여, parent=self)와 마지막 답변의 번호 승계를 확인(단위).
- 마지막 답변 커밋 후 꼬리질문 없이 클로징이 트리거되는지 확인(단위).
- 종료 사유별로 올바른 클로징 문구 세트가 선택되는지 확인(단위).
- 클로징 발화 객체가 스키마대로 적재되는지(`questionType="closing"`, 번호 생략, END 판단 시 reason 포함) 확인(단위).
- 클로징 재생 재시도 소진 시 잡 종료 없이 종료 시퀀스가 계속되고 발화 객체가 커밋되지 않는지, 마지막 질문 재생 소진 시 커밋 없이 클로징으로 진행되는지 확인(단위).
- 남은 시간이 넉넉한 픽스처에서 `FOLLOW_UP`/`FINAL_QUESTION` 경향, 사실상 0인 픽스처에서 `END` 경향 확인(LLM 스모크 — 세부 분포는 미리보기 스크립트로 수동 관찰).

### 성능 요구사항

- 마지막 질문·클로징 모두 LLM 호출이 없다(고정 문구) — 종료 국면 추가 지연 없음. 마무리 판단은 기존 Orchestrator 호출의 액션 집합 확장일 뿐이다.

### 인터페이스 요구사항

- 입력: 마무리 단계 신호·남은 시간(§1), 기존 Orchestrator 입력(현재 줄기 + 이전 대화).
- 출력(구조화): `action` — 비마무리 단계 ∈ {`FOLLOW_UP`, `NEXT_TOPIC`}(기존), 마무리 단계 ∈ {`FOLLOW_UP`, `FINAL_QUESTION`, `END`}. 나머지 필드는 기존과 동일.
- 마지막 질문·클로징 문구 목록: 코드 상수(한국어, 음성 제약 준수 — 한두 문장·plain text·구어체).

### 제약사항

- 마무리 판단은 시간 신호에 종속된다 — 비마무리 단계에서 Orchestrator가 조기 종료를 판단하는 것은 허용하지 않는다(충분히 못한 면접을 LLM 판단으로 일찍 끝내지 않는다).
- 마지막 질문 단계에서 새 주제·꼬리질문 생성은 없다(코드 강제 — 답변 1회 후 클로징).
- 평가·리포트 내용을 마지막 질문·클로징에서 언급하지 않는다(평가 노출 금지 — 선행 PRD 계승).

### 기타 요구사항

- 출력 언어는 한국어. 마지막 질문·클로징 문구도 검수 대상(프롬프트 변경 = 코드 변경 원칙).

## 3. 세션 정리·퇴장

### 설명

클로징 이후 종료 시퀀스를 순서대로 실행하고 룸을 정리한다. 어떤 단계의 실패도 퇴장을 막지 않는다.

- **종료 시퀀스(순서 고정)**: (1) 종료 상태 `CLOSING` 진입(진입 부수효과로 **종료 표식 기록** — 아래) → (2) 클로징 재생 완료(§2 — 실패 시에도 진행) → (3) **대화 로그 확정**: 신규 커밋 차단 + Redis write-through writer drain·종료(§4 — 큐에 대기 중인 append가 이후 정리된 키를 되살리지 않게 하는 순서 보장) → (4) transcript DB flush(§4) → (5) Redis 사본 정리(`DEL` — flush 성공 시에만, §4) → (6) 리포트 생성 요청 발행(§5 — flush 성공 시에만) → (7) **룸 삭제**(bounded retry) → (8) 잡 종료. 룸 삭제를 제외한 각 단계는 실패해도 로그 후 다음 단계로 진행한다(퇴장 보장).
- **유한 시간 보장(timeout budget)**: 종료 시퀀스의 모든 외부 호출(DB·Redis·LiveKit API)에 명시적 타임아웃을 둔다 — 재시도 횟수 제한만으로는 무한 대기를 막지 못한다(호출이 hang이면 재시도에 도달하지 못한다). 시퀀스 전체가 유한 시간 안에 반드시 잡 종료에 도달한다. 타임아웃 값은 config 상수 **[미확정 — 실측 조정]**.
- **종료 표식(termination marker)**: `CLOSING` 진입 부수효과로 Redis에 종료 표식을 기록한다(키: `interview:{sessionId}:termination` — 종료 원인·시각, TTL은 transcript 사본과 동일 원칙, sessionId 부재 시 생략). **transcript 행과 독립적인 종료 증거**다 — flush까지 실패한 최악 경로에서도 "이 세션은 종료 국면에 진입했다"가 남는다(클로징 재생 **전** 기록이므로 클로징 청취까지 보장하지는 않는다). 기록 실패는 best-effort(경고 로그) — 이 경우의 판별은 아래 계약의 transcript 행 우선순위가 흡수한다(행이 있으면 `ENDED`, 행도 없으면 표식 없음 경로로 후퇴). **조회 주체는 Spring이다(확정)** — Spring이 `AGENT_LOST` 처리(재dispatch 결정) **전에** 종료 표식을 직접 조회한다. 대안 기각: 재dispatch된 agent의 자가 판별은 이미 재dispatch가 일어난 뒤라 "재dispatch 금지"를 만족할 수 없고, agent→Spring 종료 API는 새 HTTP 결합을, Spring 소유 저장소 기록은 쓰기 권한 경계 위반을 만든다. 표식 키·형식 **확정** — 키 `interview:{sessionId}:termination`, 값 JSON `{"cause": "<종료 원인>", "markedAt": "<UTC ISO-8601(초 단위, Z)>"}` (현행 구현 그대로).
- **퇴장은 룸 삭제로 한다**: agent가 룸을 남겨두고 먼저 퇴장하면 Spring webhook 매핑상 `participant_left(agent)` → `AGENT_LOST`(재dispatch 시도)로 오인된다. agent가 LiveKit 서버 API로 룸을 삭제하면 `room_finished`가 발화되고, 드래프트 매핑(`ACTIVE` + `room_finished` → `ENDED`)대로 Spring이 정상 종료로 전이한다. 룸 삭제와 전후 이벤트의 경쟁은 Spring의 terminal no-op 가드가 수렴한다(계약 전제 — 후속 Spring 스토리 완료 조건으로 이관). 따라서 **룸 삭제는 best-effort 단계가 아니다** — 실패한 채 퇴장하면 방지하려던 `AGENT_LOST` 오인 경로로 그대로 진입한다. 타임아웃을 포함한 bounded retry(횟수·간격 **[미확정 — 실측 조정]**) 후에도 실패하면 오류 로그를 남기고 잡을 종료한다. 이때 Spring의 `AGENT_LOST` 처리가 종료된 면접을 잘못 재dispatch하지 않도록, **종료 표식·transcript 행 기준의 판별 계약**을 명시한다 — transcript 행만으로는 flush 실패 경로를 구분할 수 없다 (계약 **확정** — 판별 동작의 구현·검증은 후속 Spring 스토리로 이관, 아래 표):

| 우선순위 | 관측 (agent 소실 시) | 판별 | Spring 처리 |
| --- | --- | --- | --- |
| 1 | transcript 행 있음 | 정상 종료 완료(룸 정리 또는 표식 기록만 실패) | `ENDED` 정리, 재dispatch 금지 |
| 2 | 행 없음 + 종료 표식 있음 | 종료 국면 진입 후 flush 실패 | `ABORTED` 정리, 재dispatch 금지 — 이미 종료 국면에 진입한 세션이다(보존된 Redis 사본·표식이 복구 재료) |
| 3 | 둘 다 없음 | 진행 중 예기치 않은 소실 | 일반 `AGENT_LOST` — 재dispatch 가능(Agent 복원 스토리) |

  **transcript 행을 1순위로 두는 근거**: 비정상 경로는 flush하지 않으므로(§4 — DB INSERT는 정상 종료 시퀀스에서만 일어난다) 행 존재 단독으로 정상 종료의 증거다. 표식은 best-effort라 "표식 없음"이 "종료 아님"을 뜻하지 않는다 — 표식 기록만 실패하고 flush는 성공한 세션도 이 우선순위가 `ENDED`로 정확히 수렴시킨다.

  이 표의 세 경로는 **후속 Spring 스토리의 완료 조건으로 이관**한다(fallback 선기록의 판별 포함 — 아래 ack 부재 보완) — agent 측 검증은 표식·transcript 행의 기록까지고(검증 기준), 표식을 조회해 재dispatch를 막는 동작의 검증은 Spring 스토리가 담당한다(해당 이슈에 이 계약을 반영해야 이 판별이 성립한다). 이 판별은 **공유 인프라 전제**(Spring이 agent의 Redis·Postgres를 직접 읽는다) 위에서 성립하며, 이 전제의 성립 확인도 같은 후속 스토리 완료 조건으로 함께 이관한다.
- **사용자 명시 종료 수신 = 서버 API data 메시지(`SendData`) (확정)**: 프론트 → Spring `POST /sessions/{id}/end` → Spring이 LiveKit 서버 API `SendData`로 룸에 종료 신호를 보내고(topic 기반), agent가 `data_received` 이벤트로 수신해 정상 종료 시퀀스(클로징 포함)를 실행한다. 종료 요청의 관문을 Spring 하나로 유지한다(상태 단일 소스 원칙). **수신 검증(신뢰 경계)** — 다음을 모두 만족할 때만 종료 신호로 처리하고, 하나라도 어긋나면 무시한다: (1) **발신자가 서버 API일 것** — 서버 SDK 발신 data 패킷은 발신 participant가 없다(`participant is None`)는 것으로 구분한다, (2) 종료 topic 일치, (3) payload의 sessionId가 현재 세션과 일치. 특히 **참가자(candidate 포함)가 보낸 동일 topic 메시지는 무시**한다 — 프론트·참가자가 Spring 관문을 우회해 종료를 트리거할 수 없다.
  - **ack 부재 보완**: SendData는 응답이 없다(fire-and-forget) — agent의 정상 처리는 룸 삭제 → `room_finished` webhook이 사실상의 ack다. 일정 시간 내 `room_finished`가 오지 않으면 Spring이 룸을 직접 삭제하는 타임아웃 fallback을 계약에 둔다(agent가 신호를 처리하지 못하는 비정상 상태 — flush 유실 감수). 단, **fallback 삭제도 같은 `room_finished`를 발생시키므로 webhook만으로는 정상 종료와 구분할 수 없다** — Spring은 fallback 삭제 **전에** 종료 결과를 먼저 상태로 기록(선기록 후 삭제)하고, 이후 도착하는 `room_finished`는 terminal no-op으로 수렴시킨다(webhook은 룸 정리 확인 용도). fallback 계약 **확정** — 선기록 후 룸 삭제이며, **선기록도 위 판별표를 따른다**: `ABORTED`를 기록하기 **전에** transcript 행·종료 표식을 판별표와 같은 우선순위로 조회해, transcript 행이 있으면(= agent가 flush까지 완료하고 룸 삭제만 지연·실패한 경우) `ENDED`로 기록하고 룸 정리만 수행한다 — 정상 종료 세션이 fallback 경합으로 `ABORTED`로 남는 것을 막는다. 조회와 기록 사이의 잔여 경합 창은 감수한다(fallback 타임아웃을 종료 시퀀스 소요보다 충분히 크게 잡는 전제 — 값·경합 창 좁히기는 후속 스토리 실측에서). 타임아웃 값은 후속 Spring 스토리에서 확정 **[미확정 — 타임아웃 값]**.
  - topic 명칭·페이로드 스키마 **확정**: topic `interview:end`(config `INTERVIEW_END_TOPIC` 현행 값), 페이로드 `{"sessionId": "..."}`(sessionId 검증용 최소 구성).
  - **대안 비교(기각)**: (1) *프론트 → agent RPC* — 호출자가 ack를 받는 장점이 있으나, 종료 요청이 상태 머신의 단일 소스(Spring)를 우회하고 프론트가 Spring·agent 두 경로의 정합을 책임지게 되어 기각. (2) *룸 삭제로 전달* — 클로징 발화가 불가능하고, shutdown 유예 안에 flush·발행을 마쳐야 하며, "룸 삭제 = 정상 종료"와 "룸 삭제 = 비정상 정리"를 agent가 구분할 수 없어 기각.
- **오류 종료·비정상 경로와의 경계**: TTS 재시도 소진 등 진행 불가로 인한 잡 종료(선행 PRD)는 이 종료 시퀀스를 타지 않는다 — 클로징·flush 없이 종료하고 룸도 삭제하지 않는다(`AGENT_LOST` 경로로 남겨 재dispatch 여지를 보존 — Agent 복원 스토리 범위). candidate 이탈로 인한 세션 종료(현행 기본 동작)도 범위 외다 — 현행 임시 단계에서는 flush 없이 종료되며(ABORTED 상당), 재연결 스토리에서 처리한다. **오류 종료 시 사용자 안내도 범위 외로 확정한다** — 안내 채널(오류 통지 data 메시지·프론트 오류 화면)·부분 flush 여부·상태 정합(복구 가능/불가 구분 신호)이 모두 Agent 복원·프론트 스토리와 얽혀 있어 그쪽에서 함께 설계한다.
- **로컬 폴백**: sessionId 부재(콘솔·metadata 없는 로컬 dispatch 픽스처) 시 flush·리포트 발행·룸 삭제를 생략하고(각 경고 로그) 클로징·잡 종료는 동일하게 동작한다 — 종료 흐름 자체는 로컬에서 검증 가능하다.
- **운영 fail-fast**: 생략 폴백은 sessionId 부재에만 허용한다. **sessionId가 있는 잡(운영 경로)에서 DB·Redis 구성이 없으면 잡 시작 단계에서 실패 처리**한다 — 면접을 끝까지 진행해놓고 저장을 통째로 잃는 것보다 시작 거부가 낫다(구성 오류는 배포 시점에 드러나야 한다).

### 실행 조건

- agent가 LiveKit 서버 API(룸 삭제) 권한을 가진 자격증명으로 동작(`agent/.env` — 현행 자격증명으로 가능 여부 확인).
- 사용자 종료 전달은 Spring 연동 후 활성화 — 연동 전에는 soft/hard 경로만 동작.

### 검증 기준

- 종료 시퀀스가 정의된 순서(로그 확정 → flush → Redis 정리 → 발행 → 룸 삭제)로 실행되고, flush 실패·발행 실패에서도 다음 단계가 계속되어 잡이 종료되는지 확인(단위 — 의존성 주입 스텁).
- 룸 삭제 실패 시 bounded retry 후 오류 로그와 함께 잡이 종료되는지, 외부 호출이 타임아웃 내에 실패 처리되어 시퀀스가 유한 시간에 끝나는지 확인(단위).
- sessionId가 있는 잡이 DB·Redis 미구성이면 시작 단계에서 실패하는지 확인(단위).
- 외부 종료 신호(data 메시지) 수신 시 클로징 포함 정상 종료 시퀀스가 실행되는지, 종료 topic이 아닌 메시지·비정상 페이로드·**참가자 발신 동일 topic 메시지**·sessionId 불일치가 모두 무시되는지 확인(단위).
- `CLOSING` 진입 시 종료 표식이 원인·시각과 함께 정확히 1회 기록되고, 기록 실패에도 시퀀스가 계속되는지 확인(단위 — Redis write 검증은 로컬 없으면 skip).
- 오류 종료 경로(TTS 소진)가 종료 시퀀스를 타지 않는지(flush·룸 삭제 없음) 확인(단위).
- sessionId 부재 시 flush·발행·룸 삭제가 생략되고 경고 로그가 남으며 클로징·종료는 동작하는지 확인(단위).
- 룸 삭제로 `room_finished`가 발화되는지 확인(음성 통합 — LiveKit 실환경).

### 성능 요구사항

- 종료 시퀀스는 세션당 1회 — 정량 SLA 없음. 단, 사용자 종료 수신부터 룸 정리까지의 시간은 사용자가 대기하는 구간이므로 클로징 생략 여부(§2 미확정)와 함께 실측 관찰한다.

### 인터페이스 요구사항

- 입력: 종료 상태(§1), 외부 종료 신호(`SendData` — topic `interview:end`, 페이로드 `{"sessionId": "..."}` 확정).
- 출력: LiveKit 룸 삭제 호출, 잡 종료.

### 제약사항

- 세션 상태 전이는 실행하지 않는다 — Spring 단일 소스 원칙. **agent 발 신호 중 Spring 상태 전이를 유발하는 것은 룸 종료 이벤트(`room_finished`)뿐**이다(종료 표식·transcript 행은 Spring이 판별 시 조회하는 재료이지, 전이를 push하는 신호가 아니다). fallback 선기록(ack 부재 보완 — 본문 §3)은 이 제약과 별개다: agent 신호가 아니라 **Spring 자체 타임아웃**으로 실행되는 두 번째 terminal 전이 경로(확정)이며, 이후 도착하는 `room_finished`는 terminal no-op으로 수렴한다.
- Spring 측 종료 API·webhook 핸들러·상태 머신 구현은 범위 외(계약만 정의).

### 기타 요구사항

- 종료 사유(soft/hard/사용자/오류)는 enum 값으로 운영 로그에 남긴다(개인정보 아님 — 관측·디버깅 재료).

## 4. transcript DB 저장

### 설명

세션 대화 로그를 PostgreSQL `interview_transcript`에 세션당 1행 jsonb로 저장한다(ADR-E3-10의 flush 실행 — transcript 소유자인 agent가 수행).

- **flush 원본 = 메모리 완전본(확정)**: 선행 PRD가 열어둔 원본 선택(메모리 vs Redis 사본)을 메모리로 확정한다. flush는 agent가 살아있는 정상 종료 경로에서만 일어나고, 메모리 로그는 주 사본(모든 읽기의 원천)으로 항상 완전하다. Redis 사본은 best-effort(append 실패 gap 허용)라 원본 자격이 없다 — Redis의 역할은 Agent 복원(별도 스토리)뿐이다.
- **저장 형식**: `interview_transcript(session_id, content)`에 1행 INSERT. `content`는 발화 객체 배열 jsonb — **이 스토리에서 확장된 발화 객체 스키마가 곧 저장 스키마다**(변환 없음, 필드 생략 규칙 포함): 선행 PRD §4 스키마 + `final`(번호 있는 질문)·`closing`(번호 없는 인사) 유형(§2). `closing`은 선행 PRD의 "INTERVIEWER 발화는 번호 보유" 불변식에 대한 **명시적 예외**이며, 소비자(리포트)는 `questionType`으로 판별한다 — 스키마 확장은 transcript 소유자인 agent가 여기서 확정한다.
- **멱등성**: `session_id` UNIQUE 제약을 이용해 중복 flush는 no-op으로 처리한다(`ON CONFLICT DO NOTHING`) — 종료 신호 중복·재시도가 행을 중복 생성하지 않는다.
- **실패 정책**: 실패 시 1회 재시도하고, 소진되면 오류 로그를 남기고 종료 시퀀스를 계속한다(퇴장 보장 — §3). 이때 **Redis 사본을 삭제하지 않고 TTL로 남긴다** — 마지막 복구 여지(TTL 내 수동/후속 복구)다. flush 실패 시 리포트 발행은 생략된다(§5).
- **성공 시 Redis 정리**: flush 성공 직후 Redis transcript 키(`interview:{sessionId}:transcript`)를 `DEL`한다 — 개인정보 잔존을 TTL 만료보다 앞당겨 정리한다(선행 PRD가 후속 스토리로 남긴 정리 경로). `DEL`은 §3 시퀀스상 **write-through writer의 drain·종료 이후**에만 실행한다 — 적재는 비동기 큐 기반이라, drain 전에 삭제하면 큐에 대기 중이던 append가 키를 되살린다(TTL 안전망은 남지만 정리가 무효화된다).
- **DB 의존성**: agent에 PostgreSQL 클라이언트 의존성과 접속 정보(`agent/.env`)가 추가된다. 생략 폴백(경고 후 진행)은 **sessionId 부재(콘솔·픽스처 로컬)에만** 허용한다 — sessionId가 있는 운영 잡의 DB·Redis 미구성은 잡 시작 단계 fail-fast다(§3).

### 실행 조건

- §3 종료 시퀀스에서만 호출된다(정상 종료 한정 — 비정상 경로는 flush 없음).
- sessionId 존재 시에만 실행(부재 시 생략·경고 — 로컬 폴백). sessionId가 있는데 DB 구성이 없는 경우는 여기 도달하지 않는다 — 잡 시작 단계 fail-fast(§3).
- DB 의존 테스트는 로컬 인프라 없으면 skip, CI에서는 서비스 컨테이너로 실행(agent CI에 Postgres 서비스 추가 — 기존 Redis 패턴과 동일).

### 검증 기준

- flush된 jsonb가 메모리 대화 로그와 순서·스키마 모두 일치하는지 확인(write 후 read-back — 로컬 Postgres 없으면 skip).
- 같은 세션의 중복 flush가 no-op이고 기존 행이 보존되는지 확인.
- flush 실패 시 재시도 후 종료 시퀀스가 계속되고 Redis 사본이 보존되는지, 성공 시 Redis 키가 삭제되는지 확인.
- writer drain 완료 이후에 `DEL`이 실행되어 삭제 후 키가 재생성되지 않는지 확인(write 후 read-back — 로컬 Redis 없으면 skip).
- sessionId 부재 시 생략·경고 로그를, sessionId 존재 + DB 미구성 시 잡 시작 단계 실패를 확인(단위).

### 성능 요구사항

- 세션당 1회 1행 INSERT — 부하 무시 가능. 30분 대화의 content 크기는 수십 KB 수준으로 jsonb 제약과 무관.

### 인터페이스 요구사항

- 입력: 메모리 대화 로그(발화 객체 배열), sessionId.
- 출력: `interview_transcript` 1행(`session_id`, `content` jsonb). **테이블 DDL·마이그레이션은 agent가 소유·관리한다 (확정)** — transcript 소유권(쓰기 권한 경계 = 소유권 경계)과 일치한다. 스키마는 드래프트 ERD 기준(`id`, `session_id` UNIQUE, `content` jsonb, `deleted_at`). `session_id`의 FK 대상(`interview_session`)은 Spring 소유 테이블이므로 **FK 제약은 걸지 않는 것으로 확정**한다 — Spring이 `user_id`·`resume_id`도 무FK로 가는 방침과 일관하며, 마이그레이션 적용 순서가 Spring 스키마에 결합되지 않는다. 적용 방식(마이그레이션 도구 vs 초기화 스크립트)은 구현에서 결정.

### 제약사항

- 세션 중 중간 flush는 하지 않는다(ADR-E3-10 — write 최소화, Redis 유실 리스크 감수).
- `interview_session` 등 Spring 소유 테이블에는 쓰지 않는다(쓰기 권한 경계 = 소유권 경계).

### 기타 요구사항

- flush 실패 로그에 대화 내용을 포함하지 않는다(예외 타입·sessionId만 — 기존 로그 프라이버시 원칙).

## 5. 리포트 생성 요청 발행

### 설명

flush 성공 후 리포트 생성을 비동기로 트리거하는 메시지를 발행한다. 리포트 생성 자체는 worker의 별도 스토리다.

- **발행 시점: flush 성공 직후에만**. 리포트는 DB의 transcript를 읽으므로, flush가 없으면(실패·생략) 발행도 생략한다(오류 로그) — transcript 없는 리포트 요청은 소비자를 실패시킬 뿐이다.
- **채널: Redis Stream(`XADD`)**. worker가 FastStream 컨슈머로 소비한다(드래프트 §7.6의 비동기 평가 큐). 스트림 키는 `report.generation.requested`(확정 — worker 합의), 컨슈머 그룹은 worker 스토리에서 확정.
- **메시지는 포인터다**: 전사 본문을 메시지에 넣지 않는다 — worker가 session_id로 DB에서 읽는다. 페이로드(확정 — worker 합의): `{"session_id": ...}` **단일 필드**. 발행 시각은 별도 필드로 넣지 않는다 — 스트림 entry ID(`<밀리초 타임스탬프>-<시퀀스>`)에 내장돼 있고, 단일 Redis 서버 시계 기준이라 agent 벽시계보다 일관적이다.
- **실패 정책**: 발행 실패 시 1회 재시도(타임아웃 포함 — §3), 소진 시 **식별 가능한 오류 로그**(sessionId 포함 마커)를 남기고 종료 시퀀스를 계속한다(§3). 이 경우 유실되는 것은 트리거뿐이고 transcript는 DB에 있다 — **"transcript 행 존재 & 리포트 없음"이 미발행 검출식**이다. 미발행 감지·재발행(reconciliation)은 "추후"가 아니라 **리포트 생성 스토리(worker)의 완료 조건으로 이관을 명시**한다 — 이 계약을 해당 스토리 이슈에 반영해야 이 스토리의 실패 정책이 성립한다. 이관하는 완료 조건: (1) transcript 존재 + 리포트 부재 세션의 감지, (2) 재발행으로 리포트 생성, (3) 기존 발행과 경합해도 sessionId 기준 결과가 정확히 1개(소비 측 멱등). 해당 worker 이슈를 이 스토리의 연관 이슈로 연결한다.
- **대안 비교(transactional outbox — 채택 안 함)**: transcript INSERT와 발행 요청을 같은 트랜잭션에 쓰고 별도 퍼블리셔가 스트림으로 중계하면 dual-write 유실이 구조적으로 사라지지만, 세션 단위로 뜨고 사라지는 agent 수명 모델에 상주 퍼블리셔·outbox 테이블 인프라가 추가된다. 검출식과 재발행 책임(worker)이 정의된 현 구조로 시작하고, 미발행이 실측에서 반복되면 outbox(또는 worker가 outbox 테이블을 직접 소비)로 전환한다 **[미확정 — worker 스토리 협의 시 재검토]**.
- **멱등성 전제**: 재시도로 같은 세션의 메시지가 중복 발행될 수 있다 — worker가 sessionId 기준으로 멱등 처리한다는 것을 계약에 명시한다(소비 측 dedupe).

### 실행 조건

- §3 종료 시퀀스에서 flush 성공 시에만 호출.
- Redis 접속은 기존 transcript 사본과 같은 구성(`agent/.env`)을 공유한다. sessionId 부재 시 발행 생략·경고(로컬 폴백), sessionId 있는 잡의 Redis 미구성은 잡 시작 단계 fail-fast(§3).

### 검증 기준

- flush 성공 시에만 발행되고, flush 실패·생략 시 발행이 생략되는지 확인(단위).
- 발행된 메시지의 스키마(session_id 단일 필드)를 확인(write 후 read-back — 로컬 Redis 없으면 skip).
- 발행 실패 시 재시도 후 종료 시퀀스가 계속되고, sessionId를 포함한 식별 가능한 오류 로그가 남는지 확인(단위).

### 성능 요구사항

- 세션당 1회 XADD — 부하 무시 가능.

### 인터페이스 요구사항

- 입력: sessionId, flush 성공 여부.
- 출력: Redis Stream 메시지(키·스키마 **[미확정]**).

### 제약사항

- 리포트 생성·평가 로직, 컨슈머 구현, 리포트 완료 통지(프론트)는 범위 외.
- 메시지에 대화 내용·개인정보를 넣지 않는다(sessionId는 개인정보 아님).

### 기타 요구사항

- 스트림 잔존 관리(MAXLEN·소비 후 정리)는 worker 스토리와 함께 확정 **[미확정]**.
